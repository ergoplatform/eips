Abstract
--------

This EIP adds `VerifyStark` (`0xB9`) for deterministic native verification of
one bounded STARK receipt in an ordinary Ergo transaction. Its four-child ABI is
stable; immutable compiled profiles are content-addressed and activated by
authenticated network generations.

The first profile targets RISC Zero v3.0.5 shipping succinct `lift`, `join`, and
`resolve` paths, with fixed worst-case precharge, fail-closed quarantine,
whole-input future fallback, and separate non-consensus admission controls.

The initial profile is an interoperability profile. Its current security
estimate is about 95 conjectured classical bits under the stated toy model,
below 128. This is model-dependent, is not a proven lower bound, and may be
materially lower under more conservative analysis. This EIP makes no end-to-end
post-quantum-security claim.

Motivation
----------

A STARK verifier has a large rigid body of arithmetic, hashing, transcript work,
and parsing; ordinary ErgoScript adds interpreter and accounting overhead. A
consensus-native operation can:

- execute one frozen predicate with bounded proof and input sizes;
- charge its full native work before proof-controlled computation;
- bind the result to the network, profile, program, contract, and application
  payload;
- support a direct one-transaction proof path; and
- retain one stable script ABI while later immutable verifier profiles are
  activated through network consensus.

The opcode verifies a proof. It does not run a prover or execute a zkVM inside
the node.

Goals and non-goals
-------------------

The initial activation is designed to:

- accept receipts emitted by a pinned shipping prover profile;
- accept the pinned prover's bounded single- and multi-segment succinct paths;
- admit only one byte-exact proof encoding;
- keep parsing, allocation, verification, and payload work bounded;
- remain safe under negation, short-circuiting, dead branches, and dynamic expression materialization;
- allow fail-closed network quarantine without changing the profile identity;
- allow nondecreasing repricing without changing proof validity; and
- fit a realistic signed transaction in one block.

It does not provide:

- arbitrary RISC Zero receipt verification;
- identity normalization, union, unwrap, proof-of-verifiable-work, or any
  terminal recursion program outside the exact profile allowlist;
- script-selected fields, hashes, FRI parameters, control roots, circuit layouts, security levels, or work estimates;
- `vmType`, `costParams`, or another transaction-declared difficulty field;
- a generic AIR interpreter, dynamically loaded verifier, or consensus plugin;
- an on-chain STARK-profile registry;
- SP1, Valida, or the earlier Ext16/Poseidon1 research profile at initial activation;
- a bridge or multi-transaction proof-chaining protocol;
- automatic privacy, spending authority, replay prevention, nullifier handling, or application-state validation; or
- an end-to-end post-quantum guarantee.

1. Normative conventions
------------------------

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT,
RECOMMENDED, MAY, and OPTIONAL state requirements on conforming implementations.

For this EIP:

- `A || B` is byte concatenation.
- `ASCII(s)` and `UTF8(s)` are the exact string bytes; every domain tag is ASCII.
- `u8(x)` is one unsigned byte; `u16le(x)` and `u32le(x)` are unsigned
  little-endian integers of exactly two and four bytes.
- All length, offset, multiplication, addition, and cost arithmetic is checked;
  overflow is invalid and wraparound forbidden.
- `Int.MaxValue` is `2_147_483_647`.
- `BLAKE2b-256` is the native 32-byte BLAKE2b output, not a truncation of
  BLAKE2b-512.
- Digests use raw byte order; lowercase hex is display encoding, not reversal.
- Lexicographic ordering of byte strings compares bytes as unsigned values.
- Every byte grammar defined by this EIP requires strict EOF at its stated
  length; padding, ignored extensions, alternate encodings, and trailing bytes
  are invalid. The inherited ordinary `ValueSerializer` prefix rule in Section
  10 is not an EIP-defined byte grammar and keeps its stated opaque-suffix
  semantics.
- A JVM `Byte` may be signed, but `Coll[Byte]` preserves each raw eight-bit
  pattern.

Conformance vectors, benchmarks, source-code pins, and the cryptographic
rationale are evidence. They do not create consensus behavior.

2. Normative authority
----------------------

Consensus authority is partitioned:

| Source | Sole authority for |
|---|---|
| This EIP's global rules | Opcode, ABI, statement, trusted context, evaluation order, lifecycle outcomes, activation/version gates, future fallback, exception classes, and global dispatch-cost semantics |
| Profile manifest | Profile-owned transport and payload bounds, accepted control identifiers, and exact artifact references |
| Algorithm artifact | Profile proof grammar, canonicalization, transcript, claim construction, verifier control flow, rejection rules, and output comparison |
| Binary-data artifact | Numeric tables, dimensions, indices, and constants consumed by the algorithm artifact |
| Cost schedule | Metering value for one immutable profile, never verifier semantics |
| Transition manifest | One chain and generation's lifecycle snapshot, schedule association, `dispatchJit`, and activated validation-update bytes |

The manifest and its two referenced artifacts form one immutable, compiled-in
profile package, never transaction input or a runtime plugin. Dispatch by
`profileId` selects a vetted implementation already compiled into the node. A
new profile therefore requires a node release and an authenticated network
activation; it cannot be installed as runtime data or native code. Validity,
cost, lifecycle, and admission policy remain separate; `profileId` does not
commit to lifecycle or cost.

Before activation, any conflict among this EIP's required package contents, the
manifest, and either artifact invalidates the package. After activation,
implementation divergence from an unambiguous package MUST be corrected under
the same `profileId`; an ambiguous, defective, or unsafe package MUST instead be
quarantined, and any repaired predicate MUST use a new `profileId`.

No prose, vector, benchmark, or upstream implementation may silently add a
same-ID acceptance rule.

B1-B3 are closed for the corrected preactivation candidate. Sections 6 and 15
are its human-readable construction and decoded-review target; the
content-addressed package is the sole runtime authority if activated, and this
prose MUST NOT become a parallel verifier. Any preactivation disagreement blocks
activation and reopens affected deliverables; regeneration produces a new
downstream identity, never a second authority under the same `profileId`.

3. Opcode and ErgoScript ABI
----------------------------

The raw opcode byte is:

```text
0xB9
```

Its ErgoScript signature is:

```scala
verifyStark(
  proofChunks:         Coll[Coll[Byte]],
  applicationPayload: Coll[Byte],
  programId:           Coll[Byte],
  profileId:           Coll[Byte]
): Boolean
```

The AST node has exactly four children in that wire order. The opcode payload
is the four ordinary Sigma `Value` encodings in sequence. There is no
EIP-specific arity byte and no fifth child.

The parser MUST read and type-check:

```text
Coll[Coll[Byte]], Coll[Byte], Coll[Byte], Coll[Byte]
```

Serialization order does not define evaluation order. Section 12 defines the
only valid evaluation sequence.

`costParams`, `vmType`, and transaction-selected verifier parameters do not
exist. A proof never declares the work that the verifier will perform.

Spending an input containing this opcode requires ErgoTree language version 4
or later and the network activation described in Section 11.

4. Trusted host context
-----------------------

Evaluation requires a non-script-visible host capability containing:

- `chainDomainId`, exactly 32 bytes;
- `protocolGeneration`, an authenticated nonnegative integer;
- validation purpose: full received-block or historical validation,
  mempool/API admission, or local candidate construction; and
- the immutable historical transition tables supported by the binary.

The node assigns validation purpose and context as follows:

- full received-block or historical validation uses that block's exact state
  context after processing its extension and canonical `Parameters.update`,
  but before validating its transactions;
- mempool or submission-API admission uses the upcoming context derived from
  the current canonical tip and is recomputed after every relevant tip change;
- local candidate construction uses the exact candidate context after applying
  its proposed extension and parameter update, but before its transactions;
  and
- a read-only diagnostic API MUST explicitly select a concrete consensus
  context and MUST NOT label a diagnostic result as mempool admission.

Purpose is supplied only by the trusted node caller. A missing or inconsistent
purpose/context pair is an implementation invariant failure, never a script,
API, or configuration choice.

The exact generation source is:

```text
ErgoStateContext.currentParameters.parametersTable(Parameters.BlockVersion)
```

It is not the three-bit ErgoTree language version, a `Byte` projection of block
version, height alone, wall-clock time, API input, or mutable node
configuration.

`chainDomainId` is the raw 32 bytes obtained by Base16-decoding the height-1
genesis `Header.id` (`ModifierId`) in canonical Ergo byte order. It is not the
UTF-8 hex text, genesis state digest or AVL root, network prefix, whole-digest
reversal, or per-word reversal.

Ergo mainnet uses:

```text
b0244dfc267baca974a4caee06120321562784303a8a688976ae56170e4d175b
```

Every test or private chain activation package MUST pin that chain's exact
genesis block ID. This EIP assigns no generic permanent ID to every network
called "testnet".

Scripts, context variables, transactions, APIs, and local configuration MUST
NOT override any trusted-host field.

5. ErgoStatementV1
------------------

The opcode constructs the bytes committed by the guest. The script supplies
`applicationPayload`, `programId`, and `profileId` through three of the four
opcode children. The trusted host derives `chainDomainId` and `contractId`;
`proofChunks` is not part of the statement.

| Offset | Size | Field |
|---:|---:|---|
| 0 | 26 | `ASCII("Ergo.VerifyStark.Statement")` |
| 26 | 1 | version `0x01` |
| 27 | 32 | `chainDomainId` |
| 59 | 32 | `profileId` |
| 91 | 32 | `programId` |
| 123 | 32 | `contractId` |
| 155 | 4 | payload length as `u32le` |
| 159 | `n` | `applicationPayload` |
| `159+n` | 0 | EOF |

```text
ErgoStatementV1 =
  ASCII("Ergo.VerifyStark.Statement") ||
  0x01 ||
  chainDomainId ||
  profileId ||
  programId ||
  BLAKE2b-256(SELF.propositionBytes) ||
  u32le(applicationPayload.length) ||
  applicationPayload
```

The fixed prefix is 159 bytes. Under the initial profile's 16,384-byte payload
limit, the maximum statement length is 16,543 bytes.

`contractId` binds a proof to the executing contract, not to one box instance.
When an application's security model requires instance, transition, replay, or
ordered-output binding, the contract MUST encode the relevant `SELF.id`, state
token or NFT, state commitment, nonce or nullifier, inputs, or outputs inside
`applicationPayload` and validate them against the actual Ergo transaction
context. The guest MUST bind its proof or public statement to the exact payload
fields on which it relies. The required fields are application-specific;
neither side's checks substitute for the other's, and the opcode does not infer
them. Section 19.2 states the corresponding security requirement.

If the guest verifies an inner or aggregate proof, the application MUST make
the guest cryptographically bind that proof's externally relevant public
statement, or a canonically encoded, authenticated root commitment to that
statement, to `applicationPayload`. Verification of an opaque inner proof or
inner root alone does not establish application facts such as amounts,
destinations, or nullifiers.

The guest MUST commit exactly these bytes, for example with:

```rust
env::commit_slice(statement_bytes)
```

No prefix, suffix, alternative encoding, or trailing byte is accepted.

### 6.1 Algorithm artifact

The algorithm artifact is a canonical ASCII document defining:

- proof parsing and canonicalization;
- transcript behavior and read order;
- ordered verifier pseudocode and index spaces;
- profile-specific claim construction;
- every rejection condition; and
- final output comparison.

Its bytes MUST be ASCII only, use LF line endings, contain no BOM, CR, or NUL,
and end in exactly one LF.

### 6.2 Binary-data artifact

The binary-data artifact contains only numeric tables, dimensions, indices, and
constants consumed by the algorithm. For the initial profile these include
BabyBear/Ext4 arithmetic, Poseidon2 and RNG constants, FRI/STARK parameters,
dimensions, groups, `TapSet`, ordered `PolyExt` data, and any precomputed
protocol absorption whose complete preimage is owned by that artifact.

It MUST NOT define control flow, parsing, rejection rules, or output
comparison. It MUST NOT independently repeat or pre-absorb a manifest-owned
value.

Global host logic consumes `exactProofBytes` and
`maxApplicationPayloadBytes` directly before entering the algorithm. Where
profile verification needs `outerPo2`, the inner control root, or a terminal
control ID, the algorithm MUST consume the named manifest field. No artifact
independently owns a transport or payload check. Any numeric structure derived
from a manifest field has one specified deterministic derivation;
disagreement invalidates the package before activation.

The ordered `PolyExt` data uses distinct field-variable and mix-variable index
spaces and exact backward references. Algebraically equivalent reordering or
DAG rewriting is not conformant.

### 6.4 RISC Zero succinct Manifest V1

Manifest format `0x01` identifies this exact RISC Zero succinct grammar. It
is not an upstream-version field or a generic zkVM-family selector.

The proposed corrected manifest is exactly 458 bytes:

| Offset | Size | Field |
|---:|---:|---|

The ten control entries are fixed in this canonical order:

1. eight entries with `controlKind = 1` (normal lift) and `parameter = 15..22`;
2. one entry with `controlKind = 2` (join) and `parameter = 0`; and
3. one entry with `controlKind = 3` (resolve) and `parameter = 0`.

No other kind or parameter is defined by Manifest V1. The `parameter` of a
normal-lift entry is the RV32IM segment `po2`; the zero parameter on `join` and

difficulty.

```text

```

Strict startup and runtime validation of the compiled Manifest V1 package
requires:

- exactly 458 bytes before any field is accessed;
- version `0x01` and checked decoding of every scalar field;
- positive `exactProofBytes` and exactly ten fixed-position typed control
  entries;
- the literal kind/parameter sequence `(1,15)..(1,22),(2,0),(3,0)`;
- one 32-byte root and ten pairwise-distinct 32-byte control IDs in raw digest
  order;
- artifact kind `1` followed by artifact kind `2`;
- nonzero artifact lengths equal to the compiled artifact byte lengths;
- recomputation and equality of every artifact envelope and digest;
- recomputation of `profileId` from the exact raw manifest and equality with the
  profile ID referenced by the compiled transition package;
- checked offset and length arithmetic; and
- EOF at byte 458.

Unknown versions, padding, aliases, reordered or relabeled controls,
extensions, and trailing bytes are invalid.

`maxApplicationPayloadBytes` is a profile-owned `u32`, not a V1-global
16,384-byte constant. The generic V1 decoder parses any canonically encoded
`u32`, but conforming node software MUST reject, while constructing a compiled
profile runtime and before that runtime can enter an active transition
snapshot, values greater than
`2_147_483_488 = 2^31 - 1 - 159`. This is the largest payload whose 159-byte V1
statement prefix still fits the common signed-32-bit host length domain. Each
activation package MUST select a protocol-reviewed, resource-safe value no
greater than that arithmetic ceiling. The initial-profile construction check
requires exactly `16_384`. Every invocation remains bounded by the ordinary
transaction and collection limits before profile verification begins.

Sections 6.4 and 15 give the decoded review target for every displayed scalar,
kind, parameter, root, and control ID. Strict runtime package validation consumes those
fields from the final raw manifest and authenticates them through its
`profileId`; it does not compare them with a second hard-coded prose table. A
different raw manifest necessarily has a different `profileId` and is
unavailable unless a separate compiled transition activates it.

The manifest carries no redundant zkVM-family, suite, codec, provenance,
security, chain, program, cost, or lifecycle fields.

7. Canonical proof chunking
---------------------------

Every fixed-size profile using this ABI derives one unique partition from its
manifest-owned `exactProofBytes`:

```text
chunkCapacity = 65_535
chunkCount = ceil(exactProofBytes / chunkCapacity)
```

`exactProofBytes` MUST be positive. Every non-final chunk has exactly 65,535
bytes. The final chunk has exactly:

```text
exactProofBytes - 65_535 * (chunkCount - 1)
```

All arithmetic is checked before allocation or concatenation. No chunk count or
length array is repeated in the manifest.

For the initial profile:

```text
proofChunks.length    = 4
proofChunks[0].length = 65_535
proofChunks[1].length = 65_535
proofChunks[2].length = 65_535
proofChunks[3].length = 26_063
total                 = 222_668
```

An alternate partition is invalid even if concatenation would yield the same
bytes.

8. Fixed cost schedule
----------------------

The initial profile has one outer proof shape, one bounded payload, and terminal
allowlist cardinality `K = 10`. Lift `segmentPo2`, join, and resolve never select
query count, Merkle topology, verifier loop, or cost. A fixed worst-case native
precharge replaces all script-declared work parameters.

`CostScheduleFixedV1` is exactly 37 bytes:

| Offset | Size | Field |
|---:|---:|---|
| 0 | 1 | version `0x01` |
| 1 | 32 | `profileId` |
| 33 | 4 | `fixedJit` as positive `u32le` |
| 37 | 0 | EOF |

```text
scheduleId =
  BLAKE2b-256(
    ASCII("Ergo.StarkCostScheduleId.v1") ||
    0x00 ||
    u32le(37) ||
    scheduleBytes
  )
```

Both cost fields have the checked unsigned domain:

```text
1 <= fixedJit    <= 2_147_483_647
1 <= dispatchJit <= 2_147_483_647
```

Decoding rejects values above `Int.MaxValue` before constructing `JitCost`.

`fixedJit` covers maximum admitted statement/claim construction and hashing,
canonical proof handling, transcript, parsing, verifier arithmetic, and bounded
allocations. It is charged in full before `programId`, payload, or proof
evaluation, equally for valid, malformed, tampered, named late-reject, and
proof-valid expected-claim-mismatch paths. Ordinary expression and transaction
costs remain additive.

Generation-versioned `dispatchJit` covers trusted-context access, snapshot
selection, profile-ID validation, lifecycle lookup, and dispatch. Every executed
invocation pays it, including malformed, absent, and quarantined IDs.

`JitCost.toBlockCost` is the existing nonnegative conversion:

```text
toBlockCost(x) = floor(x / 10)
```

Activation requires:

```text
jitSum = checkedJitAdd(dispatchJit, fixedJit)
nativeBlockCost = floor(jitSum / 10)
nativeBlockCost <= active maxBlockCost
```

Addition precedes conversion. Activation is invalid unless `jitSum` is a
positive signed 32-bit JIT cost, and implementations MUST NOT separately convert
and add rounded charges. The complete canonical transaction, including ordinary
costs, MUST also fit the active block-cost limit.

For every STARK-changing manifest after the first manifest for its chain:

```text
newDispatchJit >= oldDispatchJit
```

For every same-`profileId` `Active -> Active` carry-forward or repricing:

```text
newFixedJit >= oldFixedJit
```

No fixed-cost comparison exists for `Absent -> Active` (no old schedule) or
`Active -> Quarantined` (no new schedule); every applicable same-`profileId`
decrease is forbidden.

Nodes MUST NOT infer semantic equivalence or a cross-ID cost floor across
different artifact bytes or profile IDs. Every `Absent -> Active` profile needs
fresh B5 calibration; activation review MUST reject a new identity intended or
evidenced to evade an existing predicate's floor. This is a preactivation gate,
not transaction validity. Final values and schedule identity remain blocker B5.


9. Transition manifests and lifecycle
-------------------------------------

EIP-0045 does not add an on-chain STARK registry. Each implementation contains
immutable historical transition manifests selected by authenticated chain and
protocol generation.

The resulting lookup is:

```text
T(chainDomainId, protocolGeneration)
  -> (
       dispatchJit,
       Map[profileId, Absent | Active(scheduleId) | Quarantined]
     )
```

### 9.1 StarkTransitionManifestV1

Every generation that changes STARK state has one canonical full-snapshot
manifest:

| Offset | Size | Field |
|---:|---:|---|
| 0 | 1 | version `0x01` |
| 1 | 32 | `chainDomainId` |
| 33 | 4 | `protocolGeneration` as checked `u32le <= Int.MaxValue` |
| 37 | 32 | `previousTransitionId`, or 32 zero bytes for the first manifest |
| 69 | 4 | positive `dispatchJit` as checked `u32le <= Int.MaxValue` |
| 73 | 4 | `activatedUpdateLength` as `u32le` |
| 77 | `m` | exact canonical activated-update bytes |
| `77+m` | 2 | `entryCount` as `u16le` |
| `79+m` | variable | exactly `entryCount` entries, then EOF |

Each entry is:

```text
profileId[32] ||
lifecycle:u8 ||
scheduleLength:u32le ||
scheduleBytes[scheduleLength]
```

Lifecycle `0x01` means `Active` and requires:

- `scheduleLength == 37`;
- strict `CostScheduleFixedV1` decoding and EOF;
- schedule version `0x01`; and
- equality between the entry `profileId` and the schedule `profileId`.

`scheduleId` is recomputed from those exact 37 bytes using Section 8. It is not
serialized as a second field, and an implementation-local alias or lookup key
MUST NOT replace that derivation.

Lifecycle `0x02` means `Quarantined` and requires
`scheduleLength == 0`.

Lifecycle `0x00` is never serialized. An unlisted exact 32-byte ID is
`Absent`. Every other lifecycle value is invalid.

Entries MUST be unique and sorted by unsigned lexicographic order of raw
`profileId` bytes. A manifest is a complete snapshot: every profile previously
introduced remains listed. No entry may disappear and become implicitly
`Absent`.

```text
transitionId =
  BLAKE2b-256(
    ASCII("Ergo.StarkTransitionManifest.v1") ||
    0x00 ||
    u32le(manifestBytes.length) ||
    manifestBytes
  )
```

The raw manifest, complete preimage, and expected `transitionId` MUST be
published.

### 9.2 Activated validation update

Let `priorG` be the authenticated generation in the parent state context and
`newG` the generation returned by the current block's canonical
`Parameters.update`. A STARK activation comparison occurs only when
`priorG != newG` and `newG` is an exact compiled STARK-changing manifest
generation. For that transition, `activatedUpdate` is the
`ErgoValidationSettingsUpdate` returned as the activated-update component of
the same calculation. State processing and candidate construction MUST use
this identical pure old-context-to-new-context transition.

A generation transition MUST NOT jump over an unapplied compiled STARK
manifest. Among manifests with generation greater than `priorG` and not greater
than `newG`, there must be none, or exactly one whose generation equals
`newG`; otherwise the generation transition is invalid.

The bytes stored in the transition manifest are exactly:

```text
ErgoValidationSettingsUpdateSerializer.toBytes(activatedUpdate)
```

No EIP-0045-specific re-encoding is permitted. The value is not the raw
proposed extension field, `validationSettings.updateFromInitial`, or a
re-serialization of all historical updates.

Physical absence of the proposed-update extension field is interpreted by the
existing parameters parser as `ErgoValidationSettingsUpdate.empty` before the
state transition. Its canonical serialized vector is:

```text
activatedUpdateLength = 2
activatedUpdateBytes  = 00 00
```

The activation package MUST reproduce that vector with the reference
serializer and an independent serializer. The initial manifest instead
contains the complete actual activation update, including the cumulative
`ChangedRule` value for rule 1002 that preserves earlier activated opcodes and
adds `0xB9`.

For the STARK activation-comparison transition defined above, the node MUST
compare the actually activated serialized update byte-for-byte with the
manifest before validating that block's transactions. Empty/non-empty mismatch,
reordering, mutation, or additional bytes at that STARK-changing generation is
invalid.

Later blocks with `priorG == newG`, and generation transitions that merely
inherit an earlier STARK snapshot, perform no synthetic STARK update
comparison. At such blocks, ordinary parameter-update rules apply; bytes
identical to an earlier STARK update neither select nor reactivate that
manifest.

### 9.3 Per-chain sequence and carry-forward

For each `chainDomainId`, compiled STARK manifests form a sequence ordered by
strictly increasing `protocolGeneration`:

- the first manifest has a zero `previousTransitionId`;
- every later manifest names the `transitionId` of the immediately preceding
  STARK manifest for that chain;
- no two manifests for one chain have the same generation; and
- a generation with no STARK-changing manifest does not create an implicit
  manifest.

For authenticated generation `G`, `applicable(G)` is the manifest for the same
chain with the greatest generation not greater than `G`.

- If no such manifest exists, the opcode is `OpcodeUnavailable`.
- Otherwise, `dispatchJit`, profile map, schedules, lifecycle state, and
  selected `transitionId` are exactly those in `applicable(G)`.
- Intermediate non-STARK generations inherit that complete snapshot without
  modification.

Lookup is recomputed from the purpose-specific context in Section 4: historical
block context for block validation, tip-derived upcoming context for admission,
and proposed candidate context for construction. It MUST NOT substitute height
alone, local configuration, wall clock, or a context belonging to another
purpose.

#### 9.3.1 Trusted suffix or snapshot initialization

The existing reference-node bootstrap path may initialize an accepted light or
suffix state without replaying every parameter transition from genesis. Such an
initialization does not synthesize, compare, or claim to have observed earlier
EIP-0045 transition-update bytes, and the no-jump rule in Section 9.2 applies
only to canonical transitions actually processed from the initialized parent
context.

This exception does not create an EIP-0045 trust source. The initialized state
and its authenticated generation MUST already be accepted by the node's
existing snapshot/suffix security model. The node MUST then select only the
compiled `applicable(chainDomainId, G)` snapshot for that exact initialized
generation, authenticate every package required by it, and fail initialization
if the chain, manifest sequence, runtime, schedule, or artifact is missing or
inconsistent. Operator configuration cannot supply or replace any of those
values. The first subsequently processed canonical generation transition uses
the initialized `G` as `priorG` and follows Sections 9.2 through 9.4 normally.

A full replay from genesis receives no exception. Nor may a node use suffix
initialization to validate a block under a tip-derived, candidate, or otherwise
different purpose context.

### 9.4 Allowed transitions

Comparing a new full snapshot with its predecessor permits only:

| Previous | Next | Rule |
|---|---|---|
| `Absent` | `Active` | permitted at a new authenticated generation |
| `Active` | `Active` | same immutable predicate; nondecreasing schedule |
| `Active` | `Quarantined` | permitted fail-closed transition |
| `Quarantined` | `Quarantined` | mandatory carry-forward |

The following are forbidden:

- `Absent -> Quarantined`;
- `Quarantined -> Active` or `Quarantined -> Absent`;
- entry removal;
- verifier or profile-package change under the same `profileId`;
- lifecycle-byte reinterpretation;
- `fixedJit` decrease; and
- `dispatchJit` decrease.

Quarantine has no administrator key, RPC command, configuration override, or
mutable local switch. Under EIP-0045 it is irreversible on a given canonical
history; repair requires a new `profileId` and a new network activation.

Every `Absent -> Active`, `Active -> Quarantined`, repricing, or
`dispatchJit` increase requires an authenticated network generation and a
release containing the exact snapshot. One generation MAY contain a reviewed
batch.

A binary claiming support for a generation but missing a required manifest,
profile package, verifier, or schedule has a startup or implementation
invariant failure. It MUST NOT reinterpret the missing item as `Absent`.

`transitionId` is a canonical release-artifact identity; EIP-0045 does not add
it to block extensions. Rule 1002 authenticates opcode availability, not the
profile package. An explicit on-chain transition commitment would require a
separate EIP.


10. Version lanes and whole-input materialized-feature closure
--------------------------------------------------------------

The ordinary outer-ErgoTree version check occurs first, in its historical
position. EIP-0045 MUST NOT move recursive materialization ahead of that check.
Any public preflight/continuation API MUST apply this same check itself: a
preactivation higher-version tree is rejected, while an ordinary stale-node
future-version terminal is returned without an executable continuation.
After it, the interpreter uses two disjoint lanes.

For an outer v0-v3 ErgoTree, implementations MUST preserve the exact historical
single-pass `DeserializeContext` and `DeserializeRegister` preparation,
substitution, charging, failure, and live-evaluation behavior. The existing
pass visits occurrences present in the prepared outer AST, including dead
branches, once. It does not revisit a `DeserializeContext` or
`DeserializeRegister` introduced by bytes inserted during that pass. EIP-0045
MUST NOT parse or charge bytes hidden behind such a newly inserted nested
occurrence and MUST NOT make a historically failing nested substitution
succeed.

The v0-v3 lane adds only a structural language-version guard. It maintains a
monotone `seenVerifyStark` flag seeded by a structural scan of the prepared root.
During the exact historical one-pass substitution, every successfully parsed
and inserted subtree is structurally scanned once and may set the flag. The scan
does not execute user logic, iterate substitution, or inspect bytes behind a
newly inserted nested deserialization node.

An ordinary deterministic parse, type, canonicality, resource, arithmetic, or
cost failure from the historical pass remains final. A recognized ordinary
soft-fork terminal result is returned only when `seenVerifyStark` is false; once
the flag is true, the deterministic outer-language-version failure takes
precedence and cannot be erased by a later soft-forkable occurrence. On normal
completion, a true flag likewise causes the version failure before JIT or user
Boolean evaluation, including when the observed opcode is in a dead branch. A
live nested deserialization remains subject to its historical failure behavior.
The v0-v3 lane never enters the EIP-0045 recursive closure, future-generation
fallback, or profile lookup.

Only an outer v4-or-later ErgoTree already admitted by the active ordinary
language-version rules enters the complete materialized-feature closure below.
Before any user Boolean expression, collection lambda, deferred-cost wrapper,
or opcode child executes, that lane MUST compute the complete closure of:

- the outer AST;
- every subtree produced by `DeserializeContext`;
- every subtree produced by `DeserializeRegister`;
- reachable and dead branches; and
- every deserialization occurrence introduced by a successful materialization,
  until no unprocessed occurrence remains or an ordinary consensus parser,
  type, resource, arithmetic, or cost-limit failure occurs.

A materialized subtree inherits the language version of its containing outer
ErgoTree. No implementation may add a local depth, iteration, time, or memory
ceiling to v4+ consensus traversal. The only bounds are the active ordinary
SigmaState parser and resource limits, the serialized bytes selected by the
input, and the consensus cost limit.

The deterministic traversal is a depth-first worklist in canonical left-to-right
AST child order. Every deserialization occurrence in the initial root receives
a fresh unprocessed occurrence identity. Every occurrence introduced by parsed
bytes receives another fresh identity, even when its node bytes, selected source
bytes, expected type, or subtree digest equal an earlier occurrence. Structural
equality, hash equality, interning, memoization, or cycle detection MUST NOT mark
a fresh occurrence as processed or terminate traversal.

For this traversal, structural children are serialized `Value` child fields in
their schema-defined order and elements of ordered sequences in index order.
Maps, sets, type-substitution tables, caches, and other non-serialized metadata
are opaque. Their host-language iteration order MUST NOT affect occurrence
order, observations, materialized bytes, outcomes, or cost. An implementation
MUST define its traversal from the serializable AST schema rather than from an
unordered host-language container.

At the next unprocessed syntactic deserialization occurrence:

1. obtain the exact serialized subtree bytes through the structural
   context/register access permitted by that node, without running user
   Boolean logic or a collection lambda;
2. charge those bytes using the active ordinary SigmaState deserialization
   rate and checked `addCostChecked` semantics before parsing them;
3. parse, type-check, and materialize the subtree; and
4. replace the occurrence, assign fresh identities to every deserialization
   occurrence in the inserted subtree, and process that subtree at the
   occurrence position before continuing with the next sibling.

The byte source is selected by the deserialization node's syntactic context ID
or register ID; a supported known-generation form never evaluates an
expression to identify that source. A missing source or a source of the wrong
ordinary type follows the existing `DeserializeContext` or
`DeserializeRegister` semantics and does not by itself create a hidden
subtree. That occurrence is then marked processed and remains explicit for its
ordinary live-evaluation behavior. Each fresh syntactic occurrence that selects
bytes is charged even when another occurrence uses identical bytes.

For a `DeserializeRegister` with a syntactic default, processing order is exact.
The interpreter first resolves the register source and, when selected bytes are
present, charges, parses, and type-checks their one `Value` prefix. A failure in
that step is final before the default is entered. If a selected value exists,
the worklist then materializes the shadowed default subtree, materializes the
selected subtree, and retains only the selected subtree in `materializedRoot`;
`VerifyStark` occurrences are consequently recorded in default-then-selected
order. If no correctly typed register byte source exists, ordinary semantics
select the default, which is materialized exactly once and retained. Costs
already committed for selected bytes remain committed if later default
materialization fails.

The ordinary `ValueSerializer` consumes exactly one `Value` prefix starting at
source offset zero. Remaining source bytes are opaque: they are neither part of
the materialized AST nor executed or scanned for feature occurrences, but the
entire selected source byte string remains included in the pre-parse per-byte
charge. EIP-0045 adds no EOF check or whole-source reserialization-equality
rule. A malformed or wrong-typed prefix cannot recover from a valid suffix.

For `G <= Gmax`, there is no implementation-selected unresolved shortcut. The
pass continues until its worklist is empty or propagates the ordinary
deterministic parse, type, resource, arithmetic, or cost failure. An actual materialized
`VerifyStark` occurrence is then handled by Sections 11 and 12. Only an
EIP-aware stale binary at `G > Gmax` may classify materialization it cannot
understand as a potential occurrence for Section 13.

Repeated or cyclic deserialization is not a structural fixed point and is not
an uncharged shortcut. A direct self-cycle and an `A -> B -> A` cycle keep
creating fresh occurrences under the rule above until an ordinary consensus
cost/resource limit fails. Implementations MUST NOT terminate a cycle using
equality, deduplication, or a local cap.

After the byte precharge, materialization outcomes are:

| Condition | `G <= Gmax` | `G > Gmax` full block | `G > Gmax` admission/candidate |
|---|---|---|---|
| Known `Value` prefix and expected type | materialize and continue | materialize and continue preflight | materialize and continue preflight |
| Known-format malformed bytes, canonicality failure, or type mismatch | ordinary deterministic deserialization failure; retain cost | same deterministic failure | same deterministic failure |
| Unknown opcode/version classified soft-forkable by ordinary active validation rules | ordinary whole-input soft-fork result with current cost; execute no user logic | the same ordinary global whole-input soft-fork result with current cost | reject unsupported |
| Stale parser cannot establish whether future materialization contains `VerifyStark` | not applicable to a claimed-supported generation; invariant failure | potential occurrence and Section 13 fallback | reject unsupported |
| Checked overflow, cost limit, or active ordinary resource limit | propagate failure | propagate failure | propagate failure |

The implementation MUST expose one unified whole-input preflight result so an
ordinary soft-fork result and EIP-0045 fallback cannot be applied twice or use
different accumulated costs.

The materialization rows above are mutually exclusive and priority ordered.
For each occurrence, the ordinary materialization layer first returns exactly
one of:

1. an ordinary deterministic parse, type, canonicality, resource, arithmetic,
   or cost failure;
2. a recognized ordinary soft-fork result; or
3. for an EIP-aware stale binary only, an explicit
   `UnresolvedFutureMaterialization` classification without an ordinary
   soft-fork result.

The first result propagates as an ordinary failure. For `G <= Gmax`, the second
terminates whole-input preflight using the ordinary global soft-fork result and
the current `preflightBlockCost`. At `G > Gmax`, it produces that same result
only for full-block or historical validation; admission and candidate purposes
return unsupported rejection as specified in the table. Only the third may be
classified as a potential `VerifyStark` occurrence for Section 13. An
implementation MUST NOT infer the third result from the second, apply both
results, or replace an ordinary soft-fork result with EIP-0045 fallback. If its
ordinary materialization layer cannot distinguish the third result, full-block
or historical validation MUST preserve the ordinary soft-fork result, while
future-generation admission/candidate MUST reject unsupported; neither purpose
may synthesize a STARK-specific unresolved result.

The only successful normal-continuation result is:

```text
ContinuePreflight(materializedRoot, preflightBlockCost)
```

This is semantic notation, not a requirement to expose `materializedRoot` as a
publicly constructible value. An implementation MAY bind it to an opaque,
single-use continuation, provided no caller can substitute a different root,
resume it twice, or enter evaluation before the complete preflight result is
available.

`materializedRoot` is the exact result after the v4+ worklist is empty. Every
processed occurrence that selected bytes is replaced by its materialized value.
A missing or wrong-ordinary-type source that existing ordinary semantics leave
unsubstituted remains explicit in `materializedRoot` and follows that ordinary
live-evaluation behavior.

The ordinary outer-tree preparation/substitution charge is included exactly
once in `preflightBlockCost`, and every occurrence that selected bytes incurs
its ordinary deserialization-byte charge exactly once. Normal evaluation MUST
receive `materializedRoot`, not the original root, through
`context.withInitCost(preflightBlockCost)`. It MUST NOT rerun the substitution
pass, reparse selected bytes, or recharge an already processed occurrence. The
JIT evaluator initializes exactly once with
`JitCost.fromBlockCost(preflightBlockCost)`, adds subsequent ordinary expression
and native JIT costs, and converts its final total normally. No caller adds
`preflightBlockCost` again after reduction.

This single-charge handoff is not a cache discount. Repeated syntactic
occurrences selecting identical bytes each pay once during preflight; cache
reuse may change runtime only.

Outer-tree preparation and substitution use the active ordinary SigmaState
costing rules, including the existing `CostPerTreeByte` and
`CostPerByteDeserialized` authorities. This EIP does not duplicate their
numeric values. The feature scan adds no wall-clock, cache-hit, or
implementation-specific charge.

`preflightBlockCost` is not a profile cost or schedule. It is the current
ordinary block-cost accumulator value at the exact whole-input preflight exit:

- the accumulator begins with the input context's `initCost`;
- all ordinary preparation and every selected subtree byte charge described
  above are retained;
- fallback MUST return the current value, never a value captured before
  partial materialization.

The accumulator is already in block-cost units. It MUST NOT be passed through
`toBlockCost` again. If normal evaluation continues, existing SigmaState
machinery performs its ordinary conversion when initializing the JIT evaluator;
EIP-0045 introduces no second meter or conversion.

Checked consensus-arithmetic overflow and cost-limit exhaustion are
deterministic validation failures that make the evaluated input invalid. They
are never converted to fallback or Boolean `false`. They are distinct from host
OOM or missing implementation material, which produce no ledger-validity
verdict under Section 14.

Feature and parsed-subtree caches are consensus-transparent optimizations. For
identical input bytes, context, generation, and validation purpose, warm and
cold execution MUST produce the same:

- materialized closure;
- version and profile observations;
- fallback, rejection, or exception class;
- `preflightBlockCost`; and
- total consensus cost.

A cache hit never suppresses a per-occurrence byte charge or bypasses a type,
version, canonicality, resource-bound, or outer-tree-version check.


11. Initial opcode activation and version gate
----------------------------------------------

`G_OPCODE`, the authenticated initial-activation generation, is blocker B6.

The ordinary outer-version check and Section 10 v0-v3 lane occur first. A
structurally visible `VerifyStark`, including one introduced directly by the
historical one-pass substitution, fails that lane before and after activation.
Its monotone observation survives a later ordinary soft-fork result but not an
ordinary deterministic failure. EIP-0045 does not parse bytes hidden behind a
newly inserted nested deserialization; the legacy evaluator performs no second
substitution, so those bytes cannot execute.

For an ordinarily admitted outer v4+ tree, Section 10 preflight completes or
terminates; an ordinary deterministic failure or global soft-fork result is
final. After it returns the complete closure and fixed `preflightBlockCost`,
precedence is opcode availability then profile lookup. An early occurrence MUST
NOT skip later materialization when consensus cost would change.

At every `G < G_OPCODE`, any occurrence in an otherwise admitted complete v4+
closure causes whole-input `OpcodeUnavailable` before profile lookup, including
under negation, in dead branches, and after either deserialization operation.

Initial activation is atomic:

- spending use requires ErgoTree v4 or later;
- `VerifyStark` becomes available;
- the initial RISC Zero profile becomes `Active`;
- rule 1002, `CheckValidOpCode`, becomes a cumulative `ChangedRule` that
  preserves every previously activated opcode and includes raw `0xB9`;
- the existing validation-settings prefix `0x02` is used; and
- no prefix `0x03` is introduced.

In activation block `H`, the node computes updated parameters/settings and
verifies their exact bytes against the compiled transition manifest before
transactions. Reaching the generation without that update is invalid and does
not activate the opcode.

V4 spending is valid in `H`; public relay normally begins after preactivation
mempools apply `H`, typically `H+1`, with no artificial extra-block delay.

Output parsing retains existing forward compatibility: unknown unexecuted
proposition bytes MUST NOT retroactively invalidate an old block and MAY be
prepositioned under existing unparsed-tree rules. They cannot be spent before
v4 passes the ordinary outer-version check; afterward, the parsed script and
transaction must satisfy all then-active rules.


12. Normal invocation evaluation
--------------------------------

Only an invocation admitted by Sections 10 and 11 enters normal evaluation.
It receives the `ContinuePreflight` root and context defined in Section 10 and
MUST use this order:

1. Evaluate `profileId` only, charging its ordinary expression cost.
2. Read trusted chain, generation, and validation purpose.
3. Select `applicable(G)`, or `Tmax` only after Section 13 permits it.
4. Add `dispatchJit` to the ordinary JIT cost accumulator.
5. Require the evaluated profile ID to contain exactly 32 bytes.
6. Resolve lifecycle.
7. If `Active`, add the full `fixedJit` to the same accumulator.
8. Evaluate `programId` and require exactly 32 bytes.
9. Evaluate `applicationPayload` and enforce the manifest-owned bound.
10. Evaluate `proofChunks` and enforce the canonical partition.
11. Construct `ErgoStatementV1` and the profile-specific expected claim.
12. Parse and verify the proof.

Serialization order MUST NOT change this sequence.

Consequences:

- A profile-ID expression failure propagates normally.
- A profile ID whose evaluated length is not 32 returns `false` after
  `dispatchJit` and before the other three children.
- An exact unknown ID is `Absent`.
- `Absent` returns `false` after `dispatchJit` without evaluating
  `programId`, payload, or proof.
- `Quarantined` produces deterministic non-softforkable input failure after
  `dispatchJit` without evaluating the other three children.
- `Active` pays the complete `fixedJit` before any remaining child,
  allocation, parse, transcript, or cryptography.
- A wrong program ID length, oversized payload, noncanonical chunks, malformed
  proof, invalid proof, wrong claim, or trailing data returns `false` after the
  applicable full precharge.
- Normal child-expression failures, cost-limit failures, and checked overflow
  propagate rather than becoming `false`.

Both native charges enter the existing cost accumulator. There is no parallel
or hidden counter. For the activation fit check, implementations MUST add the
two JIT values before dividing by ten; separately rounding each charge and then
adding is nonconformant.


13. Future-generation stale-node semantics
------------------------------------------

For one binary and chain:

```text
G     = authenticated generation being evaluated
Gmax  = highest generation the binary claims to understand
Tmax  = the last STARK manifest applicable to Gmax
```

`Tmax` need not be at generation `Gmax`.

For `G > Gmax`, a structurally static `profileId` is exactly 32 bytes and is
either a literal `Coll[Byte]` constant or a constant placeholder resolved from
the containing ErgoTree. Preflight MUST NOT evaluate an expression to prove
constancy.

For full received-block or historical validation:

| Observation over every possible occurrence | Stale-node action |
|---|---|
| Closure proves no occurrence | EIP-0045 imposes no STARK-specific fallback; continue through ordinary global soft-fork logic |
| Every occurrence has a static ID known `Active` or `Quarantined` in `Tmax` | Permit only the last-known EIP-0045 semantics using `Tmax`; ordinary global soft-fork logic still applies |
| Any static ID is `Absent` or unknown in `Tmax` | Immediate whole-input fallback |
| Any ID is malformed or non-static | Immediate whole-input fallback |
| Materialization is unresolved or may hide an occurrence | Immediate whole-input fallback |

A permitted last-known active call uses the immutable old verifier,
`Tmax.dispatchJit`, and `Tmax` schedule; a last-known quarantined call fails only
if normal evaluation reaches it.

No continuation row authorizes another post-`Gmax` feature. Ordinary version
and validation-rule checks still may fail or soft-fork the whole input.

Fallback returns:

```text
WhenSoftForkReductionResult(preflightBlockCost)
```

Fallback precedes every user Boolean, lambda, deferred-cost wrapper, and opcode
child. It is a whole-input result, never an opcode-local Boolean; it retains
cost and charges no `dispatchJit` because no invocation executes.

At `G > Gmax`, mempool/API admission and local candidate construction reject
before Boolean evaluation any possible occurrence or unresolved materialization
that may hide one. A stale binary MUST NOT construct with an unknown transition.

This envelope depends on immutable historical semantics, irreversible
quarantine, nondecreasing global `dispatchJit`, and nondecreasing same-ID
`Active -> Active` `fixedJit`; it assumes no cross-ID floor. Changing global
opcode semantics, quarantine reversibility, or either monotonicity rule requires
a separate EIP and cannot reuse this fallback proof.


14. Outcomes and exception boundary
-----------------------------------

| Condition | Required outcome |
|---|---|
| v0-v3 `seenVerifyStark` is true and the historical pass has no ordinary deterministic failure | deterministic whole-input version failure; a later ordinary soft-fork result cannot erase the flag; no recursive EIP closure |
| version-admitted v4+ preflight returned normally, `G < G_OPCODE`, and closure contains the opcode | whole-input `OpcodeUnavailable` before lookup |
| evaluated profile ID length is not 32 | `false` after dispatch |
| exact unknown or `Absent` profile | `false`; heavy children untouched |
| active valid proof | `true` |
| active invalid or canonically malformed proof | `false` after full precharge |
| wrong program ID, payload, claim, chunks, or trailing data | `false` after full precharge |
| `Quarantined` | deterministic non-softforkable input failure |
| future full-block structural uncertainty | whole-input soft-fork result with `preflightBlockCost` |
| future admission/candidate possible occurrence | unsupported rejection before Boolean evaluation |
| cost limit or checked consensus-arithmetic overflow | deterministic validation failure; evaluated input is invalid |
| child-expression evaluation failure | propagate normally |
| OOM or host allocation failure | abort validation without a ledger-validity verdict |
| missing required table, verifier, artifact, or schedule | startup or implementation invariant failure; no ledger-validity verdict |

The native verifier MAY catch only enumerated invalid-proof and
canonical-format failures and convert those to `false`. It MUST NOT use
`catch (Throwable) => false`.

Cost, quarantine, future preflight, child evaluation, allocation, and invariant
failures remain distinguishable. Quarantine MUST NOT return `false` because
negation would turn that result into success.

OOM, host allocation failure, and missing implementation material are not
consensus outcomes of a transaction. A node encountering one MUST stop that
validation attempt without declaring the input or transaction ledger-invalid.
Conforming releases prevent missing-material cases at startup.


15. Initial RISC Zero profile
-----------------------------

### 15.1 Provenance and accepted receipt family

The reproduction anchor and independent oracle is RISC Zero v3.0.5 commit
`8eb06ab020a92dc5b63ba6dd0836d432aba6d890`. It generates evidence and
cross-checks the frozen package; it is not a runtime dependency and cannot
redefine an activated profile. Its exact producer configuration and source map
are recorded in the
[cryptographic rationale, Section 6](eip-0045-cryptographic-rationale.md#6-first-risc-zero-profile)
and the content-addressed algorithm artifact.

The initial profile accepts only succinct receipts whose reconstructed
outermost recursion code root uniquely matches one manifest entry:

```text
normal lift_rv32im_v2 for segment po2 in [15, 22]
join
resolve
```

It rejects identity/final normalization, union, unwrap,
proof-of-verifiable-work, every other terminal recursion program, non-OK final
claims, and non-empty final assumptions.

Terminal join supports stock multi-segment compression, including ancestry in
which a child is resolved before the final join. Terminal resolve supports
assumption discharge when `resolve` itself is the outermost program.
The verifier imposes no pure-lineage rule: the outermost terminal is allowlisted
and the decoded inner root and exact final claim are checked, but child control
IDs carried as private witnesses are not filtered. Section 15.3 defines the
resulting trust boundary. The algorithm artifact remains the sole runtime
authority for these profile-specific paths.

The inner control root commits to the broader upstream set of 27 recursion

MUST independently enforce both the exact manifest-owned root and the
ten-entry typed terminal allowlist above. A receipt with identity, union,
unwrap, PoVW, or any other stock-root member as its terminal is rejected.

proof output MUST contain the pinned inner root above, but that check does not
expose or restrict child control IDs carried as witnesses by the terminal
program. An allowed terminal join may therefore contain children produced by
`po2 = 14` lift, identity, PoVW, unwrap, resolve, or another recursion control.
A terminal resolve may discharge an `Assumption` carrying any explicit control
root committed by the guest; a zero control root denotes self-composition under
the conditional receipt root. These are RISC Zero typed claim semantics, not
an assertion that Ergo silently trusts an arbitrary root.

`programId` binds the guest code and therefore the guest-side trust policy.
Applications and their contracts MUST select and enforce assumption roots and
their provenance safely. `VerifyStark` enforces the outermost terminal ID,
pinned decoded inner root, and exact final expected claim; it does not audit a
guest's application-specific assumption policy. The exact final expected claim
still requires OK status and empty assumptions.

The raw seal carries no host-wrapper `controlId`, control kind, parameter, or
segment exponent declaration. After reconstructing the code Merkle root from
the raw seal, the verifier MUST derive the accepted entry as follows:

```text
computedCodeRoot = reconstructed code Merkle root
matches = manifest.entries.filter(entry => entry.controlId == computedCodeRoot)
require matches.length == 1
matchedEntry = matches[0]
require decodedOutputInnerRoot == manifest.innerControlRoot
```

Manifest validation already requires pairwise-distinct control IDs, but the
runtime comparison remains exact and fails closed unless one entry matches.
Neither caller input, reproduction metadata, nor an upstream receipt wrapper
may select the entry. Raw seal word 32 is the recursion circuit exponent 18; it
is not a terminal kind, a lift segment exponent, or a work declaration.
Comparing `computedCodeRoot` to the immutable allowlist is the direct-ABI
replacement for the generic upstream `control_inclusion_proof`. The decoded
output inner-root check is separate and does not substitute for this code-root
comparison.

### 15.4 Raw seal transport and canonical parsing

The transaction carries only the raw succinct seal:

```text
55_667 u32 words * 4 bytes = 222_668 bytes
```

Every word is little-endian. The bytes do not contain a receipt enum, journal,
claim, image ID, host vector length, or other host-language serialization.
Field elements and Poseidon2 digest words use RISC Zero's reduced BabyBear
Montgomery representation. An implementation MAY convert to another internal
representation, but MUST apply the exact artifact-defined decoding; treating a
stored word directly as an ordinary canonical BabyBear integer is invalid. The
`outerPo2` word is the protocol's raw inserted value and is checked separately.
Every field-element and Poseidon2-digest word MUST be strictly less than
`2_013_265_921` before reinterpretation. Word 32 is the literal raw `u32` value
18, inserted upstream with `Elem::new_raw(po2)`; it MUST NOT be
Montgomery-decoded before comparison.

The complete zero-based word census is:

| Word span | Count | Content |
|---|---:|---|
| `0..31` | 32 | recursion output |
| `32` | 1 | outer `po2` |
| `33..288` | 256 | code Merkle top |
| `289..544` | 256 | data Merkle top |
| `545..800` | 256 | accum Merkle top |
| `801..1056` | 256 | check Merkle top |
| `1057..3692` | 2,636 | 659 Ext4 `coeff_u` values |
| `3693..3948` | 256 | FRI round-1 top |
| `3949..4204` | 256 | FRI round-2 top |
| `4205..4460` | 256 | FRI round-3 top |
| `4461..4716` | 256 | 64 final Ext4 coefficients |
| `4717..55666` | 50,950 | 50 query records of 1,019 words each |

Each query record has this relative layout:

| Relative word span | Count | Content |
|---|---:|---|
| `0..131` | 132 | accum leaf 12 plus 15 sibling digests |
| `132..274` | 143 | code leaf 23 plus 15 sibling digests |
| `275..522` | 248 | data leaf 128 plus 15 sibling digests |
| `523..658` | 136 | check leaf 16 plus 15 sibling digests |
| `659..810` | 152 | FRI-1 leaf 64 plus 11 sibling digests |
| `811..930` | 120 | FRI-2 leaf 64 plus 7 sibling digests |
| `931..1018` | 88 | FRI-3 leaf 64 plus 3 sibling digests |

The initial Merkle tops are read in `code, data, accum, check` order, whereas
query openings are read in `accum, code, data, check` order. An implementation
MUST NOT reuse one ordering for the other. The checked total is:

```text
33 + 1_024 + 2_636 + 768 + 256 + 50 * 1_019 = 55_667 words
```

The only accepted chunk partition is the one derived in Section 7. Alternate
partitions, empty chunks, truncation, added bytes, and trailing words are
rejected before cryptographic verification.

Zero-based seal-word indices 0 through 15 contain the Poseidon2 inner-root
slot. Each raw word in indices 0 through 15 MUST first be range-checked against
the BabyBear modulus and Montgomery-decoded as specified above. The eight raw
padding words at indices `1, 3, 5, 7, 9, 11, 13, 15` MUST equal zero; no
ignored alternate encoding is accepted. The decoded values at the even
indices are the eight ordinary `u32` words used to construct the root digest.

Zero-based seal-word indices 16 through 31 inclusive encode SHA-256
halfwords. Each raw word MUST first be range-checked against the BabyBear
modulus and Montgomery-decoded. Each resulting ordinary `u32`, not the raw
wire word, MUST then be at most `0xffff` and is extracted as one little-endian
`u16`. Raw Montgomery words are generally greater than `0xffff`; checking or
truncating them as halfwords before decoding is invalid. Silent truncation is
forbidden.

The transcript follows the pinned Poseidon2 RNG and fixed-consumption
`ReadIOP` behavior encoded by the algorithm artifact. It has no
implementation-defined rejection-sampling loop. Strict EOF is required after
the final expected read. This profile performs no FRI grinding and reads no
grinding nonce; an implementation that expects or ignores such a word is not
conformant.

The verifier enforces:

- raw seal word 32 equals the literal `u32` value 18;
- exactly one selected typed terminal control among the ten manifest entries;
- the exact inner control root;
- the exact expected claim; and
- complete proof consumption.

#### 15.4.1 Metering census boundary

The successful verifier topology is fixed by the profile. Terminal kind and
normal-lift parameter do not select a query count, Merkle depth, verifier path,
or cost; every accepted terminal receives the same `fixedJit`.

For each profile, B5 MUST either prove that every accepted shape has the same
bounded verifier cost, including its operation and allocation topology, or
derive the fixed charge from the worst accepted shape. A profile that needs
shape-dependent charging is incompatible with this EIP's
`CostScheduleFixedV1` and complete pre-heavy-child charge. It requires a
separate EIP or opcode defining a new schedule format and evaluation order; no
transaction, script, or proof may declare the shape's cost.

Before B5 closes, the completed implementation MUST publish a reproducible
operation, allocation, and peak-live-memory census that reconciles every
semantic step of the algorithm artifact. It MUST include parsing and range
checks, transcript/RNG work, Merkle and FRI verification, field arithmetic and
inversions, generated constraint execution, expected-claim construction and
comparison, checked cost accounting, allocations, dispatch, and SigmaState
integration. One-time authenticated profile-construction work MUST be
identified separately from per-invocation work. The valid path, named early and
late rejects, final expected-claim mismatch, and peak-allocation path MUST all
fit the prepaid envelope.

Exact reference counts and their derivation are audit evidence, not additional
wire fields or mandatory implementation instruction boundaries. They are kept
in the [cryptographic rationale, Section 8.2](eip-0045-cryptographic-rationale.md#82-why-the-constants-are-still-unset)
and the [implementation plan, Task 12.1](docs/plans/2026-07-17-eip-0045-implementation-plan.md#task-121---build-a-complete-operation-and-allocation-census).

The upstream wrapper's `control_inclusion_proof` is absent from the direct
transaction ABI and MUST NOT enter consensus parsing or cost. Reproduction
tooling that ingests a wrapper MUST first bound and canonically validate that
wrapper and require its terminal ID to match one manifest entry; it cannot use
wrapper metadata to select a terminal or change raw-seal semantics.

### 15.5 Program ID and expected RISC Zero claim

`programId` is exactly the RISC Zero guest image ID in the 32-byte order
returned by `Digest::as_bytes()`. It is not text, a whole-digest reversal, four
reversed `u64` words, or eight reversed `u32` words.

The frozen algorithm artifact was generated and reviewed against the following
decoded claim-construction target. The artifact is the sole runtime authority
and this display is not a second executable definition. Let
`H(x) = SHA-256(x)`, `Z` be 32 zero bytes, `I = programId`, and
`J = ErgoStatementV1`:

```text
TS(tag, down[], data[]) =
  H(
    H(UTF8(tag)) ||
    down[0] || ... || down[n-1] ||
    u32le(data[0]) || ... || u32le(data[m-1]) ||
    u16le(n)
  )

journalDigest = H(J)

post =
  TS("risc0.SystemState", [Z], [0])

output =
  TS("risc0.Output", [journalDigest, Z], [])

expectedClaim =
  TS("risc0.ReceiptClaim", [Z, I, post, output], [0, 0])
```

This is an OK receipt claim with empty assumptions. Every other claim is
rejected.

The pre-B3 diagnostic claim values formerly shown in this section are
superseded and are not conformance evidence. B4 remains open until the final
identity-bound corpus publishes every statement input and intermediate, then
proves the complete host-builder-to-real-receipt chain against the frozen

17. Admission-layer work control
--------------------------------

Consensus cost protects block validation, not unpaid admission work. Every node
supporting an active profile MUST enforce one bounded controller across API,
unconfirmed P2P, mempool, revalidation, and candidate paths:

- before recursive v4+ closure, acquire a coarse global CPU/memory permit and
  debit the applicable per-source budget;
- after structural preflight, atomically reserve the profile-weighted work and
  memory for every possible invocation, or a conservative aggregate bound,
  before native parsing or cryptography;
- bound aggregate memory and concurrent verification, never reserving less for
  malformed or invalid proofs than for a valid proof of the same profile; and
- bound exact replay suppression and any semantic cache by entries, bytes, and
  lifetime, prevent API/mempool double verification, and route activation,
  repricing, quarantine, and reorg revalidation through the same globally
  bounded queue without charging an old peer.

Work units MUST be deterministic profile units, not milliseconds or a
CPU-specific ratio. Worker count, local caps, rates, cache policy, peer scoring,
and defer-versus-reject behavior remain node policy. Exhaustion causes admission
rejection/defer or candidate skip; it MUST NOT change received-block or
historical validity.

The implementation details and stress matrix are maintained in the
[implementation plan, Phase 11](docs/plans/2026-07-17-eip-0045-implementation-plan.md#15-phase-11---admission-and-candidate-protection).

18. Reorg and historical-state behavior
---------------------------------------

Every lookup uses the purpose-specific context defined in Section 4:
historical block context for block validation, tip-derived upcoming context for
admission, and proposed candidate context for construction. No mutable
singleton may hold current STARK capability.

Consequently:

- a reorg below initial activation restores no applicable STARK manifest and the
  opcode-unavailable capability state; because v4 is no longer admitted, an
  attempted v4 spend fails the ordinary outer-version check before capability
  lookup and no EIP recursive closure runs;
- a reorg below quarantine restores the preceding `Active` snapshot;
- a reorg across repricing restores the historical schedule;
- quarantine is not retroactive to blocks validated under an earlier snapshot;
  and
- mempool transactions are evicted or readmitted after each relevant
  transition or reorg.

A transaction disallowed after quarantine MAY become admissible again if the
canonical chain returns to a generation before that quarantine.


19. Security considerations
---------------------------

### 19.1 Cryptographic claim

The initial profile's current security estimate is about 95 conjectured
classical bits under the stated toy model, below 128. It is model-dependent,
not a proven lower bound or consensus parameter, and may be materially lower
under more conservative analysis. No exact decimal estimate is reproducible
evidence until its digest-bound command, inputs, and output artifact is
published. The profile makes no generic post-quantum-security claim. The
derivation, assumptions, and open review obligations are maintained in the
[cryptographic rationale](eip-0045-cryptographic-rationale.md#7-security-interpretation).

### 19.2 Statement, authorization, and replay

`ErgoStatementV1` binds the network genesis, profile, guest program, executing
contract, and application bytes. It does not automatically bind a box instance,
transaction, inputs, outputs, nonce, nullifier, or application transition.
Contracts MUST encode and consistently validate every additional binding their
security model needs in `applicationPayload`.

A guest that verifies an inner proof or aggregate root MUST bind its complete
externally relevant public statement, including authorization facts such as
amounts, destinations, and nullifiers. Applications requiring separation
between chains that intentionally share a genesis ID MUST add their own fork
domain. Proof validity never replaces ErgoScript ownership, value, token,
successor-state, or output checks.

### 19.3 Divergence and denial of service

Implementations MUST prevent digest/word reversal, alternate proof partitioning,
unchecked offsets or cost arithmetic, halfword truncation, trailing data,
transcript disagreement, duplicate profile ownership, broad exception
conversion, cache-dependent closure/cost, and current-tip substitution for
historical state. Canonical grammars and negative vectors reduce these risks but
do not replace independent review or fail-closed quarantine.

The fixed precharge protects block validation only after B5 covers the complete
valid, named late-reject, and peak-allocation paths. Size alone is not a CPU
bound. Section 17 admission controls remain separately mandatory for unpaid
work, and their local state MUST NOT affect ledger validity.

--------------------------------------------

Vectors are evidence, never alternate semantics. Every accepted field, branch,

The executable inventory is in the

Implementations MUST cover: exact four-child/golden serialization, types and
rule-1002 bytes; v4 activation and forward-compatible output parsing; byte-exact

eleven case shapes in Section 15.2. Fresh B7 seals are not required to match the
B4 archive or each other. A missing B4 case blocks B4; a missing fresh case
blocks B7. Removing a required case shape requires a new identity and EIP
revision.

Cost fixtures MUST prove dispatch on every lifecycle/ID class, full fixed
precharge before every heavy child, equal active-path valid/early/late/final-mismatch native
charging, additive ordinary costs, add-before-divide, overflow/limit/domain
boundaries, schedule monotonicity, transaction/block fit, and complete
operation/allocation/peak-memory coverage. Deterministic invalid proof and host
failure MUST remain distinct; no cost or invariant exception becomes `false`.

### 20.3 Lifecycle, transition, reorg, and node paths

For `V = verifyStark(...)`, direct, negated, Boolean, conditional, and
collection-predicate contexts MUST cover unavailable, absent, valid/invalid
active, and quarantined outcomes. Transition fixtures MUST reproduce bytes/IDs;
isolate every grammar, predecessor, lifecycle, predicate-identity, and schedule
failure; and cover strict carry-forward, missing snapshots, exact cumulative and
empty updates, activation, repricing, quarantine, rollback, and mempool changes.

Node fixtures MUST cover byte-identical JVM/sigma-rust transactions, the
262,144/262,145 relay boundary and received-block exception, candidate/block
application, both reservation stages, aggregate memory/concurrency and
global/per-source budgets, bounded replay/cache/revalidation, no API/mempool
double verification, candidate skip/defer, and admission-independent validity.

### 20.4 Reproduction and observation gates

B7 evidence MUST satisfy Section 15.2 and positive plus isolated-negative
coverage for every schema, digest, precommit/challenge, anchor/inclusion,
file-manifest, case-order/reuse, signature, declaration, and reorg rule in the
frozen
[Task 13.5 procedure](docs/plans/2026-07-17-eip-0045-implementation-plan.md#task-135---execute-and-close-the-final-b7-challenge-bound-reproduction).
These are activation-evidence failures, never transaction-validity rules.

B8 requires a `TestnetObservationPlanV1`, digest-published and anchored in a
canonical testnet output before `startHeight`, and a
`TestnetObservationReportV1` binding that plan and all raw evidence. The plan
MUST freeze:

- testnet and target profile/schedule/transition identities, activation kind
  (`InitialOpcodeProfile` or `LaterProfile`), releases/JVMs, active block
  limits, node configuration, B5 resource envelopes, fixtures, and thresholds;
- a named implementation/operator/role/machine roster with two independently
  built and operated validators, producer, relay, archival/reorg roles, slowest
  retained B5 class, and smallest supported memory class; and
- exact heights, deadline, lifecycle events, workloads, telemetry, evidence
  manifest, and every nonzero refill/expiry/revalidation/voting horizon.

Only the frozen roster counts. A later implementation needs a new or amended
predeclared campaign. Pass/fail bounds MUST be shipped hard values or
coefficient-free formulas over named protocol values; post-hoc percentiles and
safety multipliers are diagnostic only.

The plan MUST derive `Nblock` under reuse and split-transaction possibilities,
with independent byte/cost bounds and machine-checkable packing proving
`Nblock >= 1` fits and `Nblock + 1` cannot. The campaign MUST cover every
positive family, maximizing repeated calls, saturation, applicable early/late
rejects, burst/refill and sustainable-stream horizons, replay expiry, both
activation kinds, quarantine under negation, rollback, and reactivation.

Passing requires zero consensus/cost/state-root/lifecycle divergence, unexpected
crash/OOM/deadlock/unbounded growth, pre-reservation work, double verification,
or hard-bound breach. The report MUST digest-bind logs, metrics, blocks,
transactions, forks, and final state; missing required evidence or event fails.
Any bound consensus/profile/schedule/transition/limit/calibration/admission/plan
change forces a new plan and full rerun. A proven logging-only change MAY retain
the run only with unchanged bound binary/configuration digests.

Exact evidence IDs, schemas, anchors, path grammar, lifecycle/workload vectors,
and report validation live in the
[implementation plan, Task 14.3](docs/plans/2026-07-17-eip-0045-implementation-plan.md#task-143---execute-the-predeclared-testnet-observation).
They are deployment gates, not consensus inputs.

21. Activation gates
--------------------

Mainnet activation is forbidden until all of the following are complete:

1. Freeze the algorithm and binary-data grammars and exact bytes.
2. Have two independent implementations reproduce both artifact digest preimages and digests.
3. Independently reproduce the 458-byte manifest, 485-byte preimage, and final `profileId`.
4. After identity fixation, generate the exact eleven-case Section 15.2 B4
   archive, its final statement/claim values, and its closed isolated-negative
   registry.
5. Have the official Rust and JVM verifiers agree on every B4 positive,
   ancestry edge, root branch, and negative, then freeze the archive;
   separately, each of two clean B7 environments MUST anchor a distinct
   precommit and generate and verify all eleven fresh challenge-bound case
   shapes.
6. Publish a hermetic RISC Zero lock: repository/commit, crate/source paths, Cargo features and `Cargo.lock` digest, host Rust 1.89 and guest 1.88.0 toolchains, guest-builder OCI digest/platform, host/guest targets, build profile, local-prover settings, and deterministic extraction/KAT commands.
7. In both clean B7 environments, reproduce deterministic artifacts and
   archived verification results byte-for-byte, validate the immutable B4 file
   digests, and verify every fresh receipt without requiring its randomized
   seal bytes or digest to match B4 or the other run.
8. Complete the JVM operation/allocation, valid/invalid/late-reject/final-mismatch, throughput, and peak-memory census.
9. Freeze and independently audit `dispatchJit` and `fixedJit`, including joint block-limit fit.
10. Exact schedule bytes and `scheduleId` are reproduced independently.
11. Prove exact v0-v3 compatibility and v4+ closure/future-preflight charge-before-parse, no user-expression execution, no cost rollback, and cache equality.
12. Freeze and reproduce exact cumulative rule-1002 bytes including `0xB9`.
13. Freeze and reproduce the initial transition manifest, activated-update bytes, `transitionId`, generation, and chain-domain mapping.
14. Pass node block, mempool, candidate, activation, quarantine, repricing, and reorg integration tests.
15. Release, stress-test, and deploy the 256 KiB policy and bounded admission controller before activation.
16. Close independent consensus and cryptographic reviews without unresolved critical findings, and complete Section 20.4's predeclared testnet plan with a passing digest-bound report.
17. The exact mainnet transition manifest is reviewed before miner voting.

Passing unit tests or publishing this draft does not satisfy these gates.


22. Future compatible profiles
------------------------------

A later RISC Zero version or another zkVM may reuse `VerifyStark` only if it
preserves the four-child ABI, `ErgoStatementV1` and trusted-host model,
canonical bounded direct transport, global evaluation/precharge order,
lifecycle/quarantine, exact v0-v3 behavior, v4+ closure and future fallback,
exception boundary, and cost monotonicity.

Every new profile MUST have a new immutable manifest and `profileId`, complete
algorithm and binary-data artifacts, a separately calibrated schedule, an
authenticated `Absent -> Active` transition, complete positive and
isolated-negative vectors, and independent implementation/security review. Its
bounds MUST be representable by every conforming host and Sigma collection
type, include a protocol-reviewed safe payload ceiling no greater than the V1
arithmetic limit in Section 6.4 and enforced while constructing the compiled
profile runtime before it can enter an active transition snapshot, cover peak
live memory, and admit a canonical transaction with `Nblock >= 1` under active
block size and cost.
Where direct public relay is claimed, a compatible standalone-transaction
policy MUST be deployed before activation.

Adding such a profile is a node-release event: `profileId` dispatches to its
vetted compiled verifier module only after authenticated network activation. A
profile is never installed from a transaction, registry entry, runtime data
bundle, or dynamically loaded plugin.

Fresh B5 calibration and the Section 20.4 observation gate apply to every new
activation. A profile that is unrepresentable, cannot fit one invocation, or
cannot meet its frozen resource envelope MUST NOT activate. Later same-profile
repricing remains nondecreasing under Section 8.

Manifest V1 belongs only to the initial RISC Zero v3
`lift`/`join`/`resolve` shape. Another package structure needs a new
manifest format and compiled verifier. Incompatible arguments, statement
binding, transport, evaluation order, dynamic resource selection, or fallback
require a new opcode or separate EIP; existing `profileId` semantics never
change.

23. Rejected alternatives
-------------------------

The initial design rejects transaction-declared difficulty/cost parameters, a
full on-chain profile registry, one ErgoTree version per zkVM, executable
descriptors or runtime plugins, benchmark-only/hardware-ratio costing,
multi-transaction proof chaining, and the earlier Ext16/Poseidon1 research
profile. The security and compatibility reasons are recorded in the
[cryptographic rationale, Section 12](eip-0045-cryptographic-rationale.md#12-rejected-alternatives).
None of these approaches may reinterpret this opcode or an existing
`profileId`; adopting one requires the new profile or separate EIP demanded by
Section 22.
