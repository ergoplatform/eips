# EIP-0051: Rent-Paying Refresh in the Storage-Rent Grace Period

* Author: bob
* Status: Draft
* Created: 25-Sep-2026 (reworked 27-Sep-2026 as an extension of EIP-53)
* License: CC0
* Forking: Soft fork, activating together with EIP-53
* Requires: EIP-53 (interacts with EIP-48, see *underfunded*)

## Abstract

EIP-53 gives an expired, underfunded box holding tokens or registers a two-week window
in which it can be refreshed but not swept. This EIP adds two rules for that window:

1. **Every refresh pays one rent** into a fixed output that anyone may spend 720
   blocks later.
2. **A plain P2PK box can pay with its own tokens.** The refresher may keep a share of
   each token, starting at 2^-32 and doubling every 315 blocks up to 1/2.

Underfunded boxes then pay the same rent as funded ones. Valuable P2PK holdings are
rescued by the first producer who finds it profitable, and the owner pays about one
to two rents in tokens instead of losing everything. Nothing refers to the header's
miner key, so the rent works with collateralized pools such as Lithos.

## Motivation

EIP-53 removes the cliff where a box a few cents short loses everything. It leaves
two problems:

1. **Rent becomes optional for token boxes.** EIP-53 charges an underfunded box only
   down to the minimum value (360 nanoERG per byte today). A typical 112-byte token box
   holding 0.001 ERG owes 0.14 ERG of rent, but pays at most 0.00096 ERG once. After
   that, a transaction fee keeps it alive for another four years, and anyone can block
   its collection indefinitely at that price.
2. **Nobody is paid to rescue.** A refresh earns the refresher nothing, and a producer
   who includes one gives up its own chance to sweep the box later. With storage-rent
   transactions kept out of the mempool (ergo PR #2577), the most valuable boxes are
   the ones producers have most reason to let lapse.

## Specification

Terms follow EIP-53: `P = StoragePeriod` (1,051,200) and `G = StorageGracePeriod`
(10,080 = 32 × 315). For an input spending box B at height H:

* **rent-path input**: `H - B.creationHeight >= P`, an empty proof, and context
  variable 127 holding a `Short` that is a valid output index. Call that output O.
* **underfunded**: `B.value <= storageFee(B)`, with `storageFee` as consensus computes
  it at H (32-bit today, 64-bit once EIP-48 is active).
* **protected**: B is underfunded, holds a token or a register R4–R9, and
  `0 <= t < G`, where `t = H - B.creationHeight - P`.
* `rent(B) = Long(storageFeeFactor) * B.bytes.length` and
  `minValue(B) = Long(minValuePerByte) * B.bytes.length`, both in 64 bits.
* **stage**: `k = t / (G / 32)` (integer division, `0 <= k <= 31`), 315 blocks per
  stage for `G` = 10,080.

### Rule 1: refreshing a protected box

A rent-path spend of a protected box B is valid only if:

1. `O.creationHeight == H`;
2. O's script and registers R4–R9 equal B's;
3. `O.value >= minValue(B)`;
4. **tokens**: if B's ErgoTree is the canonical P2PK tree (exactly `0x00 0x08 0xcd`
   followed by a 33-byte public key), O holds exactly B's token ids, and for each id
   with total amount `a` in B, O holds a total `b` with `a - (a >> (32 - k)) <= b <= a`.
   Otherwise O's tokens equal B's;
5. O is not the output of any other rent-path input in the transaction;
6. the transaction pays the rent deposit (Rule 2).

For protected boxes, Rule 1 replaces EIP-53's refresh condition. All other EIP-53
rules are unchanged. The retained amount is always at least half, and amounts below
`2^(32-k)` cannot be reduced, so NFTs are never taken.

### Rule 2: rent deposit

A deposit output has ErgoTree exactly R, `creationHeight == H`, no tokens, no
registers R4–R9, and is not the output O of any rent-path input. The deposits' total
value, summed in 64 bits, must be at least the sum of `rent(B)` over the
transaction's protected inputs. It may come from B's own ERG or from other inputs.

### Deposit contract R

```scala
sigmaProp(HEIGHT - SELF.creationInfo._1 >= 720)
```

Version-0 ErgoTree, 15 bytes (compiled with node v6.0.6):

```
100104a00bd19299a38cc7a7017300
```

From 720 blocks after the refresh, anyone may spend a deposit to any output. Creation
heights are non-negative (rule `txNegHeight`), so the subtraction cannot overflow.

### Cost

Rule 1 adds `tokenAccessCost` for each token of B and O. Rule 2 is one pass over the
transaction's inputs and outputs, which the verifier reads from the context.

### Activation

The token share allows token reductions that EIP-53 forbids. Adding it after EIP-53
is active would be a hard fork against EIP-53 nodes. It must therefore be decided
before EIP-53's activation height is fixed, and activate at that height, together with
condition 5 of Rule 1. The deposit only restricts, so it could also follow later.

Rule 1 is checked per input with the storage-rent path. Its condition 5 and Rule 2 are
checked once per transaction, as validation rule 125 (`txProtectedRefresh`). The rule may
not be disabled by voting, since the token share would lose its safeguards.

Soft-fork argument: an underfunded expired box may today be spent to any outputs, and
deposits are ordinary outputs. Every transaction valid under this EIP and EIP-53 is
valid under the current rules.

## Companion node policy (non-consensus)

* **Relay refreshes that extract nothing.** A transaction whose rent-path inputs keep
  all their tokens in their own outputs, send any ERG they release only to those
  outputs or to deposits, and pay the fee from other inputs gains its sender nothing.
  Relaying it even under `rejectStorageRentTxs` keeps sponsored rescues open. Token-share
  refreshes are not relayed, so they do not revive the bot race. This depends on
  `rejectStorageRentTxs` (ergo PR #2577) and is left to that PR.
* **Decline mempool transactions that spend R.** Otherwise bots race for mature
  deposits.
* **Collect and refresh in candidates.** Mining nodes add fee-less claims of mature
  deposits to their candidates, paying their reward address. Deposits maturing at the
  next height were created exactly 720 blocks earlier, so a node finds them by scanning
  the blocks 720 to 1,439 deep, beyond the rollback limit. Mining nodes may also refresh
  protected boxes whose share exceeds the cost, valued by a price source the operator
  configures (e.g. on-chain DEX pools). For Lithos this is its existing rent path:
  collect into a wallet output, then top up the pool. Such refreshes are left to
  external tooling.

## Rationale

**Every refresh pays a rent.** Rent charges for keeping a box in state for a period,
however the box was funded. A sponsor keeping an NFT or oracle box alive pays what a
funded box pays: 0.14 ERG per four years for a typical box.

**Why a delayed deposit.** The rent must leave the transaction in a way the refresher
cannot take back, or competition bids the token share down to nothing.

* Paying the including producer fails: a producer refreshes and pays itself.
* An output keyed to the header's miner key fails too, and under Lithos it pays the
  collateral lender instead of the pool.
* ERG added to the owner's box stays the owner's; rent would then be collected only
  every other period.

A producer that refreshes gets its deposit back only if it also produces the block
that collects it, roughly with probability equal to its hashrate share. Funded boxes
need no deposit, because their rent comes out of the box itself.

**Why P2PK only.** A key holder's box has no invariants beyond its key. A contract box
may hold reserves, supply or voting weights that others rely on, and draining part of
them could leave a live but corrupted contract. Other boxes keep their tokens exactly
and are rescued by sponsors. The rule reads only script bytes: no token prices, no
app-specific logic.

**Why doubling every 315 blocks.** Doubling raises the share by the same ratio at every
stage, so it works equally for small and large holdings. A refresher acts at the first
stage whose share covers its cost, so the owner pays at most about twice that cost.
Only stage 0 (2^-32) can overpay, and only for holdings worth more than about 4×10^9
rents.

Once the share covers its cost, a producer should refresh. Waiting pays only if no
competitor refreshes first, and then yields the doubled share, or after the window the
whole box, with probability about its hashrate share `s`. At the last stage a producer
refreshes rather than wait for the sweep if `s·V < Vf/2` (`V`: box value, `Vf`: its
reducible tokens), so for fungible holdings every producer below half does. Where an
NFT dominates `V`, only small producers qualify; if those that price tokens hold
hashrate `h`, the stage passes unrefreshed with probability `(1-h)^315`, about 4% at 1%.

### Worked example

C is the refresher's cost, `rent + minValue + tx fee - B.value`: about 0.14 ERG for a
typical single-token box.

| Holding value | Stage | Day | Owner pays in tokens |
|---|---|---|---|
| 10^7 C | 9 | 3.9 | 1.19 C |
| 10^4 C | 19 | 8.3 | 1.22 C |
| 100 C | 26 | 11.4 | 1.56 C |
| 10 C | 29 | 12.7 | 1.25 C |
| < 2 C | none | – | collected after the window |

Miners receive one rent per refresh.

### Concerns raised in discussion

| Concern | Answer |
|---|---|
| Owners lose everything over a few cents | P2PK holdings pay one to about two rents in tokens |
| Rent must keep paying miners | Every refresh pays a full rent; unrescued boxes are swept as before |
| Top-ups must not block collection cheaply | A refresh costs a full rent |
| No burning; the protocol can't value tokens | Nothing is burned; the schedule finds the price |
| Lithos puts the collateral lender in `minerPk` | No miner-key reference |
| Keep bots out of the mempool | Only refreshes that extract nothing are relayed |

## Security and economic considerations

* **Coarse and indivisible holdings.** The share is computed on raw units. A holding
  of two very valuable units can only be charged a whole unit, at the last stage. A
  box whose reducible tokens are worth under about 2C, such as an NFT alone, is never
  refreshed for profit; only sponsors or ERG attached at creation protect it. The
  two-rent bound assumes fine-grained amounts and competing producers.
* **Collusion.** A cartel can let a box lapse only if it includes every producer
  that would refresh (see *Why doubling every 315 blocks*).
* **Revenue timing.** Deposits mature after 720 blocks and may be claimed in batches.
* **State.** Deposits are token-free outputs that live about 720 blocks. Worthless
  boxes are collected at most G blocks later than today.

## Alternatives

| Proposal | Unrescued valuable box | Note |
|---|---|---|
| Status quo | Loses everything | |
| EIP-33 burn | Loses everything | Nobody gains |
| EIP-52 / PR #2577 | Loses everything | Changes who collects; compatible with this EIP |
| EIP-53 alone | Loses everything unless sponsored | Minimum-value boxes pay no rent |
| EIP-49 archival | Keeps assets | Hard fork, new state model |
| Rent as arrears | Keeps assets | Rewards leaving state untouched |
| Rent to the including producer | Pays almost nothing | Producers refund themselves |
| Rent into the owner's box | Pays about one rent net | Collected every other period |
| Rent to the re-emission contract | Pays one rent, spread over future blocks | Miners paid later; no deposit to collect |
| This EIP + EIP-53 | Pays one to about two rents | P2PK only |

## Reference implementation and test vectors

Draft implementation on top of the EIP-53 one (ergo PR #2586):
https://github.com/decentbob/ergo/tree/eip-51-rent-paying-refresh

* consensus: `ErgoInterpreter` (Rule 1, `checkProtectedRefreshes`) and validation rule
  125 in `ErgoTransaction`;
* policy: `ErgoMemPool.spendsRentDeposit` and `CandidateGenerator.collectRentDeposits`;
* tests: `ExpirationSpecification` and `ErgoMemPoolRentDepositSpec`. They cover stage
  boundaries, amounts at `2^(32-k)` and NFTs, several and split token ids, a
  near-canonical P2PK tree, the deposit sum over several inputs, outputs shared between
  rent-path inputs, rent-path detection, the activation boundary, the cost, and deposit
  claims.
