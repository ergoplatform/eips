EIP-0052: Miner-Attested Storage Rent Claims
============================================

* Author: CannonQ
* Status: Draft
* Created: 25-Sep-2026
* Last edited: 26-Sep-2026
* License: CC0
* Forking: Soft Fork


Abstract
--------

Today any transaction can collect storage rent from an expired box, and in practice bots racing in the mempool collect most of it. This EIP has two stages. Stage one is node policy and needs no fork: nodes decline rent claims at mempool admission, and mining nodes collect rent themselves. Stage two is one block-level consensus rule: a block that contains rent-claim transactions must list their ids in an extension field, which only the block producer can write. The producer then decides who collects rent in its block, at any transaction position and paid to any address. The storage period (1,051,200 blocks, 4 years) and the voted storage fee factor are unchanged. Neither stage changes what a claim may take from a box or how tokens are handled.


Motivation
----------

Storage rent was described from the start as miner income. The 2020 design post says "every four years a miner can charge storage rent fee by spending the box and recreating it" and, in the same post, that "anyone can spend the expired box" by supplying context variable 127 [2]. EIP-27 records the plan for the end of emission: "miners would be rewarded with transaction fees and storage rent (a unique source of mining income) after the end of emission" [1]. The stated expectation was that rational miners would replace third-party claims with their own, so that in practice rent would reach miners. In January 2025 kushti restated that rent was designed to be collectible by anyone, that a profit-maximising miner would replace sniper transactions with its own, and that many miners were not doing so [3]. In September 2026 he put it as: "in the rational setting storage rent is claimable by miners only", and described this proposal as enforcing that rational behavior [4].

Consensus does not enforce it. Once a box is `StoragePeriod` blocks old, any transaction may spend it with an empty proof by setting context variable 127 to the index of an output that recreates the box. The recreated box may hold up to the storage fee less, and when the box value does not exceed the fee the whole box may go to any output ([ErgoInterpreter.scala][s-int]:42-54, 72-84). The source states it directly: "anyone can spend the expired box" (:75). The reference miner builds no rent claims ([CandidateGenerator.scala][s-cg]:678-697).

Rent therefore goes to whoever broadcasts a claim first. In practice that is a bot watching the UTXO set, and the miner receives only the fee the bot chooses to attach. Only two pools build their own claims today [4]. The race has a second cost: competing claims on the same boxes are double-spends of one another, each is fully validated at mempool admission before the conflict is detected ([ErgoMemPool.scala][s-mp]:271-301), and replacement by fee keeps the churn going. kushti: "those bot wars sponsored by storage rent are not good for mempools" [4].

This EIP enforces the rational setting in two stages. Stage one removes the race from mempools and gives mining nodes a way to collect. Stage two makes the block producer's decision the only way a claim enters a block. Both matter most after emission ends, when fees and rent are the only miner income.

Two constraints shaped the consensus rule. Lithos, the non-custodial pool protocol, sets the header's miner key to a collateralizer rather than the miner, so any rule that routes rent to the miner key would route it to the wrong party, and its template builder depends on transaction order [4]. The rule therefore constrains neither where rent is paid nor where a claim sits in the block.

**Measurement.** Mainnet, heights 1,859,252 to 1,880,851 (26-Aug-2026 to 25-Sep-2026, 30.2 days), scanned from an Ergo node v6.0.6 with extra indices, using the consensus definition above; script, data and method in [12]. A claim is recreated when the box value exceeds its storage fee and an output reproduces the box, and fully consumed otherwise, matching the two branches of `checkExpiredBox`. Age is measured from the box's self-declared creation height, as consensus does.

Specification
-------------

### 1. Rent claim

An input of transaction `tx` in a block at height `h`, spending box `b`, is a rent claim when all three hold:

1. `h - b.creationHeight >= StoragePeriod`
2. the input's spending proof is empty
3. the input's context extension holds variable 127, its value is a `Short`, and that value is a valid index into `tx.outputCandidates`

These are exactly the conditions under which `ErgoInterpreter.verify` evaluates `checkExpiredBox` ([ErgoInterpreter.scala][s-int]:73-81). When variable 127 is present but is not a `Short` or not a valid index, the rent branch throws and Scala evaluates the box's own script instead (:82-84). Such an input is not a rent claim. A rent-claim transaction is a transaction with at least one rent-claim input.

### 2. Stage one: node policy (no fork)

* Nodes SHOULD decline rent-claim transactions at mempool admission and not relay them. This is implemented upstream in ergo PR #2577 (kushti, opened 26-Sep-2026, the day after the discussion in [4] and before this EIP was posted) [15]. This EIP defers to that PR for stage one. Its filter is simpler than the definition in Section 1 and better suited to policy: it declines any transaction with an input whose proof is empty and whose context extension holds variable 127, at the existing policy decline point after inputs are resolved and before validation ([ErgoMemPool.scala][s-mp]:272-283). Because that shape does not depend on the box's age, a pooled transaction can never become a claim while it waits, and no mempool recheck is needed. The measurement above found no transaction of that shape in 30 days that was not a consensus rent claim. A node that declines forgoes the fees third-party claims would have paid it; the measurement puts those fees at about a fifth of the value claimed.
* One open question on that PR: the same shape describes a no-charge refresh, an empty-proof spend with variable 127 whose output holds at least the box's value and takes nothing. The grace-period proposals under discussion depend on such refreshes being relayable, and PR #2577 declines them. Either the filter gains a carve-out for spends that extract nothing, or refreshes in a grace period go through block producers. That decision belongs with stage one and does not affect stage two.
* A mining node MAY build its own rent claims and place them in its candidate through the prioritized transactions path, at any position, paying any address it chooses. A zero-fee claim is fine there. Building claims needs an index of unspent boxes by creation height, which the reference node does not keep; arkadianet/ergo-scala PR #7 adds one [11], and the Rust node has one ([candidate.rs][a-cand]:499-520). Collection SHOULD be a configuration switch, and MAY take a token filter, so that operators who do not want particular tokens can leave those boxes alone.
* A miner-built claim MUST skip boxes that carry the re-emission token. Rule 123 forbids the token in any output of a transaction that spends it, while `checkExpiredBox` requires R2 preserved, so no claim on such a box is valid (EIP-48 [6]; fixed on the Rust node in arkadianet/ergo PR #225 [10]).
* The emission contract requires exactly two outputs and an exact issued amount (`outputsNum` and `correctCoinsConsumed`, [ErgoTreePredef.scala][s-etp]:87-89), so a claim cannot be merged into the emission transaction. It is a separate transaction.

Stage one alone removes the race from every upgraded mempool and lets any pool that builds claims collect. It cannot stop a bot submitting a claim directly to a pool that accepts it, and a pool that neither collects nor declines still leaks rent to bots.

### 3. Stage two: consensus rule

**Attestation field.** A new extension key space with prefix `0x03`. The single field has key `0x03 0x00` and a 32-byte value: the Blake2b-256 hash of the ids of the block's rent-claim transactions, each 32 bytes, concatenated in block order.

**Rule.** New block-section rule. Suggested id 308, the next free id after `bsBlockTransactionsCost = 307` ([ValidationRules.scala][s-vr]:280-287). Suggested name `bsStorageRentAttestation`, status fatal. Final id and name are for core developers. For a block of version 5 or later, let `C` be the ids of its rent-claim transactions in block order.

* If `C` is non-empty, the extension MUST contain the attestation field with value equal to the hash of `C`.
* If `C` is empty, the extension MUST NOT contain the attestation field.

The extension root is in the header and under the proof of work, so only the block producer can write the field. A rent claim built by anyone else enters a block only if the producer lists it. The rule says nothing about where a claim sits in the block or where its value goes, and it does not change whether a claim is valid; each claim is still validated by the existing rules.

**Candidate assembly.** A mining node MUST write the attestation field for whatever rent-claim transactions its candidate contains, evaluated at the candidate's height, and MUST write nothing when it contains none. Whether an input is a rent claim depends on the including block's height, so a pool transaction can become one while it waits; the field is computed from the final transaction list, not at admission. A producer MAY include a third party's rent claim and keep its fee; the rule makes rent producer-decided, not miner-only.

### 4. Parameters

Unchanged. `StoragePeriod` stays `4 * BlocksPerYear` = 1,051,200 blocks (4 years at 120 s). The storage fee factor stays a voted parameter, default 1,250,000.

Activation
----------

Soft fork. Every block valid under the new rule is valid under the current rules, so non-upgraded nodes follow the upgraded chain.

The rule is introduced with block version 5 and activated by the protocol's built-in soft-fork vote, the same path as the v3 rules ([ErgoTransaction.scala][s-tx]:384) and the 6.0 activation. Block version 4 is the current version ([Header.scala][s-hdr]:148). Under the mainnet voting settings a soft fork is proposed at an epoch boundary, voted on for 32 epochs of 1,024 blocks, approved when votes exceed nine tenths of those blocks, and activated 32 epochs after approval, at which point the block version increments ([VotingSettings.scala][s-vs]:9, [application.conf][s-conf]:239-245, [Parameters.scala][s-par]:140-145). Rule 308 is enforced only for blocks of version 5 and later, so all nodes switch at one height with no configured activation height. Stage one needs no activation; it ships in a point release.

Because the rule only tightens validity, enforcement does not depend on the vote count. Once a majority of hashrate enforces it, a block with an unattested rent claim is orphaned by the majority chain whatever the rest do. The vote is the coordination point that lets every node, mining or not, enforce from the same height.

Block version 5 also activates script version 4. The node maps block version to script version by subtracting one ([Header.scala][s-hdr]:150-152, [ErgoContext.scala][s-ctx]:28), and the interpreter accepts without verification any tree whose version is above the highest it supports once the activated version is also above it ([Interpreter.scala][g-int]:298-318, `MaxSupportedScriptVersion = 3` at [VersionContext.scala][g-vc]:48). That passthrough is the soft-fork design that let non-upgraded nodes follow the 5.0 and 6.0 activations. It is safe only because each of those releases paired the new block version with an interpreter that supports the new script version. The release that carries rule 308 MUST do the same: ship an interpreter that supports script version 4, with or without new language features. Otherwise, from activation, every version-4 tree is spendable with an empty proof on upgraded nodes. The reference implementation carries a test that documents this behaviour on sigma 6.0.6.

Like EIP-27's rule 123 ([ValidationRules.scala][s-vr]:258), the rule can later be disabled by the soft-fork rule vote.


Rationale and alternatives
--------------------------

Attestation is the smallest consensus change that makes rent collection the producer's decision without dictating anything else. The interpreter (shared with wallet code) is untouched, no new context data is needed, the block already carries a producer-only section, and one hash comparison does the work.

Two simpler-looking rules were considered and rejected because of Lithos [4]. A position rule, allowing rent claims only in the first transaction of a block, needs no extension field but constrains transaction order, which Lithos's template builder depends on; it was the first form of this EIP and its reference implementation exists on the same branch [13]. A routing rule, requiring every non-recreation output of a rent-claim transaction to pay the block's miner reward script, is position-free and would let pool payout software sweep rent with the block reward, but Lithos sets the header's miner key to a collateralizer, so rent would go to the wrong party and Lithos's contracts would have to move it. Attestation constrains neither.

| Option | Fork | Effect | Cost |
|---|---|---|---|
| Stage one only: mempool decline plus self-collection (this EIP's stage one; Cheese and arkadia's position [4]) | None | Race leaves upgraded mempools; collecting pools take rent | A pool that neither collects nor declines still leaks rent to bots submitting directly |
| Attestation (this EIP's stage two) | Soft | Only the producer decides which claims enter its block; any position, any payee | One extension field, one block-level rule. Template builders that collect add one field |
| Position rule: claims only at `t_0` | Soft | Same as attestation | Constrains transaction order; emission transaction moves to `t_1`; Lithos objects |
| Bind rent to the miner reward script | Soft | Same as attestation, and pool payout code sweeps rent with the reward | Routes rent to the header's miner key, which Lithos sets to a collateralizer. Needs the storage fee computed per input |
| Bind rent to the miner key in `checkExpiredBox` | Soft | As above | Changes interpreter logic shared with wallet code |
| Status quo | None | Rent goes to the fastest claimant | None |

**Distribution among miners.** Only two pools build claims today [4]. After stage one, a block from a pool without a claim builder contains no rent claim, the eligible boxes wait for the next block from a pool that has one, and rent concentrates in collecting pools until the others add a builder. Bot fees today flow into the block reward that pool software already shares with pool members; rent claimed by a pool pays to whatever address its builder chooses, and reaches pool members only if the pool shares it. This EIP does not address pool payout policy.

**Grace period.** A separate proposal under discussion would allow only recreation, not full consumption, for a period after the storage period ends [4]. That is also a tightening of `checkExpiredBox` and composes with this rule: the producer lists whatever recreations it includes, its own or a third party's.


Compatibility and security
--------------------------

* **Owners.** A signed spend has a non-empty proof, so condition 2 fails. Owners can spend their own boxes in any position.
* **Contracts that read variable 127.** Affected only when the box is past `StoragePeriod`, the proof is empty, and variable 127 is a valid `Short` index. That spend already goes through the rent branch today and fails outright when `checkExpiredBox` fails ([ErgoInterpreter.scala][s-int]:78-81).
* **Third-party recreation.** Today anyone may recreate an expired box at no charge, for example to keep a token box alive whose owner is absent. Under stage two such a transaction enters a block only if the producer lists it. Producers have no reason to refuse a transaction that pays a fee and takes nothing. Whether it reaches a producer at all is decided by the stage-one filter: as written in PR #2577 it declines the refresh shape too, so a no-charge refresh needs either a zero-extraction carve-out in that filter or direct submission to a pool.
* **Tooling.** Transaction order is unchanged. Explorers gain one optional extension field under prefix 0x03.
* **Lithos and other custom template builders.** A builder that includes rent claims computes one hash and adds one field. A builder that does not include them changes nothing.
* **Censorship.** No new power. Miners already choose block contents. The rule only removes third parties' ability to collect.
* **Reorg incentive.** Rent in `t_0` is block income, like fees. When few boxes are eligible, a large claim raises the value of reorging that block (the same class as fee sniping). Unclaimed boxes stay eligible for later blocks. EIP-45 proposes smoothing claimed rent across blocks to reduce this incentive [5].
* **Capacity.** Rent inputs per block are bounded by the size and cost left for `t_0`. Boxes that do not fit stay eligible.
* **Token handling.** Unchanged. A fully consumed box still yields its tokens to the claiming output. EIP-33 [8] proposes burning them instead; that proposal concerns the output side and composes with this rule.


Tests
-----

* Predicate boundary: `h - creationHeight = StoragePeriod - 1` is not a claim, `= StoragePeriod` is. Variable 127 typed `Int`, or a `Short` out of range, is not a claim and the box's own script is evaluated.
* Attested claims at transaction indices 1 and 3, extension carrying the hash of their ids in block order, emission transaction at index 0: accepted at block version 5, end to end through block application.
* The same block without the field: rejected by rule 308 at block version 5, accepted at block version 4.
* Field present with the ids in the wrong order, or covering only one of two claims: rejected.
* Field present in a block with no rent claims: rejected at block version 5, accepted at block version 4.
* A fee-paying third-party claim listed by the producer: accepted.
* With rule 308 disabled in the validation settings, the unattested block is accepted. This stands in for "a non-upgraded node accepts every block an upgraded producer makes".
* Candidate assembly writes the field with the correct hash when it includes a claim, writes nothing when it includes none, and writes nothing below block version 5.
* A pooled transaction that becomes a rent claim at the next height is invalidated by the mempool recheck when the decline setting is on, and kept when it is off.
* Mempool admission declines a rent claim at block version 5 as well as at version 4.
* A box with a version-4 ErgoTree and proposition `sigmaProp(false)`, spent with an empty proof, is rejected at block version 4 and accepted at block version 5 on sigma 6.0.6. This pins the passthrough described under Activation and must be inverted once the interpreter supports script version 4.
* The claim builder skips boxes carrying the re-emission token (not covered by the reference implementation, which builds no claims).


Reference implementation
------------------------

Branch `eip-storage-rent-attestation` on ergo v6.0.6, commits `9e2b4c07` (attestation rule, candidate field, tests) and `6c1360a5` (review fixes) [14]. Not yet published; it will be pushed as a pull request before this EIP is submitted. The withdrawn position rule remains on branch `eip-storage-rent-position` [13].

Stage one is implemented upstream by ergo PR #2577 [15], which this EIP defers to. The branch also carries an equivalent decline behind `declineStorageRentClaims` (default true) with a recheck in the cleanup worker, written before that PR existed; it is superseded and will be dropped from the pull request. No claim builder is included.

Stage two: prefix 0x03, the field key and the digest helper in `Extension`; rule 308 `bsStorageRentAttestation` in ValidationRules; `Header.StorageRentAttestationVersion = 5`; the rent-claim predicate in the `ErgoTransaction` companion, checking the constant's type before reading it; `ErgoState.execTransactions` takes the block's extension, collects the ids of rent-claim transactions while iterating, and validates the field after the loop using the validation settings from the state context so a soft-fork disable takes effect; `UtxoState` and `DigestState` both pass the block's extension; the candidate generator computes the ids over the final transaction list and adds the field in `mkCandidate`, so the normal, retry and emission-only paths all carry it. `ErgoInterpreter`, `Constants`, `Parameters` and the sigma dependency are untouched.

Tests: the cases above are `predicateBoundary` (three properties), `attestedClaimAnyPosition` (claims at indices 1 and 3, end to end through `UtxoState.applyModifier` with a real emission transaction at index 0, header extension root asserted), `attestedClaimDigestState` (the same block through `DigestState`), `unattestedClaimRejectedV5AcceptedV4`, `wrongDigestRejected` (wrong order, missing id, extra id, truncated value, duplicate field, wrong key in the key space), `spuriousFieldRejected`, `thirdPartyClaimAttested`, `disabledRuleAccepts`, `v4TreePassthroughAtV5`, `candidateAttests` (four scenarios through `createCandidate`, proven with the real proof-of-work scheme and applied to the state), `mempoolDeclines`, `mempoolDeclinesV5` and `cleanupRecheckInvalidatesClaim`. Untouched v6.0.6: 864 tests in the root module and 108 in ergo-core, all passing. The branch: 879 and 108, all passing, 98 suites, no failures. Six single-point mutations (digest comparison, absent-field branch, version gate, candidate field, generator height, DigestState extension) were each caught by the predicted tests.

Two limits of the reference implementation to state: a node with `verifyTransactions = false` validates no block-transaction rule, this one included; and a rule-308 failure is attributed to the extension section, so no transaction is purged from the mempool, which is correct because every listed claim is individually valid.


Related work
------------

* **EIP-33, Burn tokens in rent collection** (scalahub, 2022, open PR, not implemented) [8]. Burns tokens when a box is fully consumed instead of handing them to the claimer. Concerns what leaves the box, not who claims. Composes with this EIP unchanged. The PR discussion rejected routing seized assets to any trusted party at protocol level.
* **EIP-45, Redistribution contract for claimed storage fees** (Huginn, 2023, open PR) [5]. Smooths claimed rent over many blocks to reduce undercutting. Addresses the reorg incentive noted above.
* **EIP-48, Storage-Rent Repairs** (arkadianet, July 2026, open PR, hard fork) [6]. Repairs two defects in `checkExpiredBox`: re-emission-token boxes are rent-immune, and the fee wraps in 32-bit arithmetic above 1,718 bytes. Both are relaxations and need a hard fork. This EIP is a tightening and does not. The re-emission constraint is carried into Section 2.
* **EIP-49, Prepaid Storage Rent with Archival and Revival** (TheTrunk, September 2026, open PR, hard fork) [7]. Replaces the mechanism and removes third-party claims entirely. This EIP is the minimal soft-fork change that keeps the mechanism and changes only who may claim.
* **Rust node self-claim** (arkadianet/ergo v0.9.0) [9] and **Scala eligibility index** (arkadianet/ergo-scala PR #7) [11]. Node-policy claim builders. Section 2 depends on one of them for the reference node.
* **ergo PR #2577, storage rent transactions filtered out of the mempool** (kushti, 26-Sep-2026, open) [15]. Stage one of this EIP.
* **EIP-0051, Graduated Storage-Rent Grace Period for Token Boxes** (bob, PR #108, 26-Sep-2026, open) [16]. A grace-period rule for token boxes, built on EIP-48. Composes with stage two: a producer lists whatever refreshes it includes. It notes that refreshes must stay relayable, which is the open question on PR #2577 above.
