# EIP-0045: Native STARK Proof Verification

* Author: A. Shannon
* Status: Draft
* Created: 29-Apr-2026
* Updated: 27-Nov-2026
* License: CC0
* Forking: Soft-fork (ErgoTree v4 opcode `0xB9` and network-activated verifier profiles)

## Abstract

This EIP defines `verifyStark` (opcode `0xB9`), a consensus-native ErgoScript
operation for deterministic verification of one bounded STARK proof inside an
ordinary Ergo transaction.

The specification cleanly separates two layers:

1. **Part I — Core Opcode & Host Framework**: a stable, profile-agnostic
   four-child ABI (`0xB9`) available starting in ErgoTree v4, canonical
   statement construction (`ErgoStatementV1`), chunked proof transport
   supporting both fixed-size seals and bounded multiproofs, phased worst-case
   precharge, fail-closed quarantine, and a network lifecycle decoupled from
   `BlockVersion`.
2. **Part II — Verifier Profile Admission**: strict cryptographic, soundness,
   resource, and conformance gates required before any concrete verifier
   profile may be proposed for mainnet activation. Mainnet profiles MUST achieve
   at least **128-bit provable classical soundness** verified under
   [`ethereum/soundcalc`](https://github.com/ethereum/soundcalc) (Unique
   Decoding Regime or Johnson Bound Regime) across every reachable execution,
   recursion, and compression circuit.

An earlier RISC Zero v3.0.5/v3.1.0 prototype
([`a-shannon/eip0045@3a8f84c`](https://github.com/a-shannon/eip0045/commit/3a8f84cebe6c996bedbad50445453c4f67b137f6))
demonstrated ABI viability, recursive `lift`/`join`/`resolve` verification, and
single-transaction settlement (223 KiB proof, ~21.4 ms reference verification),
but is **explicitly retired from mainnet candidacy** because its BabyBear⁴
parameters provide only 33 bits (UDR) / 48 bits (JBR) of provable soundness.

---

## Motivation

Verifying a STARK proof requires intensive field arithmetic, transcript
hashing, Merkle authentication, polynomial folding (FRI/STIR/WHIR), and
constraint evaluation. Expressing a complete verifier in interpreted ErgoScript
incurs prohibitive AST, memory-allocation, and cost-accounting overhead.

A consensus-native operation resolves this while preserving Ergo's UTXO
security model:

- **One stable script ABI (`0xB9`)**: contracts remain forward-compatible as
  stronger proof systems emerge; new immutable profiles are activated through
  consensus without allocating new opcodes or burning 3-bit ErgoTree versions.
- **Deterministic precharge**: full native verification cost is charged before
  heavy argument evaluation, allocation, or proof-controlled computation.
- **Domain-bound statements**: Ergo constructs the canonical statement binding
  chain domain, verifier profile, guest program, executing contract, and
  application payload.
- **One-transaction settlement**: proofs fit inside a single standard Ergo
  transaction once node transaction-size policy is raised appropriately (Section
  9).

`verifyStark` verifies a proof; it never runs a prover or executes a zkVM
inside an Ergo node.

## Normative Conventions

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT,
RECOMMENDED, MAY, and OPTIONAL are interpreted as in RFC 2119.

- `A || B` denotes byte concatenation.
- `ASCII(s)` denotes exact ASCII byte encoding; every domain tag is ASCII.
- `u8(x)` and `u32le(x)` denote unsigned 1-byte and 4-byte little-endian
  integers.

# Part I — Core Opcode & Host Framework

## 1. ErgoScript Surface & Wire Encoding

### 1.1 Signature

```scala
verifyStark(
  proofChunks: Coll[Coll[Byte]],
  applicationPayload: Coll[Byte],
  programId: Coll[Byte],
  profileId: Coll[Byte]
): Boolean
```

Wire and AST argument order is fixed:

| Index | Name | ErgoScript Type | Semantics |
|---|---|---|---|
| 0 | `proofChunks` | `Coll[Coll[Byte]]` | Proof bytes partitioned into canonical chunks (Section 2.2) |
| 1 | `applicationPayload` | `Coll[Byte]` | Application-defined public payload (`0..maxApplicationPayloadBytes`) |
| 2 | `programId` | `Coll[Byte]` | Exact 32-byte guest program / verification-key digest |
| 3 | `profileId` | `Coll[Byte]` | Exact 32-byte immutable verifier profile identifier |

The opcode carries no transaction-declared security level, hash choice, FRI/STIR
parameter, or cost hint. All verifier semantics are fixed by the immutable
profile selected by `profileId`.

### 1.2 Opcode & ErgoTree Version Gating

- **Opcode byte**: `0xB9` (`OpCodes.VerifyStarkCode`, `LastConstantCode + 73`).
- **Minimum ErgoTree version**: `4` (`VersionContext.StarkVerificationVersion`).

Serialization, compilation, and interpretation MUST enforce strict ErgoTree
version gating so upgraded nodes remain 100% consensus-compatible with pre-EIP
v6.0.x nodes prior to activation and cannot introduce an unvoted output split or
legacy soft-fork bypass:

1. **Parse and serialize gate (`ValueSerializer` & `ErgoTree.withSegregation`)**:
   `0xB9` is recognized ONLY when `VersionContext.current.isV4OrLaterErgoTreeVersion`
   (`ergoTreeVersion >= 4`). For `ergoTreeVersion` in `0..3`, encountering
   `0xB9` during serialization or deserialization MUST fail with
   `CheckValidOpCode(0xB9)`:
   - a v0 ErgoTree without the size bit throws `SerializerException` (identical
     to pre-EIP v6.0.x nodes);
   - a v0–v3 ErgoTree with the size bit produces `UnparsedErgoTree` carrying
     `CheckValidOpCode(0xB9)` (identical to pre-EIP v6.0.x nodes).
2. **Spend-time legacy rejection (`Interpreter`)**: Even after soft-fork rule
   `1002` enables `0xB9` for ErgoTree v4+, an upgraded node MUST reject with
   `StarkOpcodeErgoTreeVersionException`:
   - any spend of an `UnparsedErgoTree` whose wire header version (`bytes(0) & 0x07`)
     is `< 4` and whose parse error is `CheckValidOpCode(0xB9)`;
   - any v0–v3 ErgoTree that directly contains `VerifyStark` or introduces
     `0xB9` via `DeserializeContext` or `DeserializeRegister`.
   This is a strict soft-fork subset rule and prevents any pre-v4 output
   carrying `0xB9` from becoming anyone-can-spend after activation.
3. **Compiler gate (`SigmaTyper`)**: Compiling `verifyStark(...)` when targeting
   ErgoTree version `< 4` MUST fail with a `TyperException`.

### 1.3 Preservation of Single-Pass Deserialization on ErgoTree v4

ErgoTree v4 MUST preserve Ergo's existing single-pass `DeserializeContext` and
`DeserializeRegister` substitution (`applyDeserializeContextJITC` and
`ErgoLikeInterpreter.substDeserialize`):

- ErgoTree v4 introduces **no** recursive nested deserialization; nested
  `DeserializeContext` retains existing evaluation-time failure semantics with
  bounded stack depth.
- Wrong-typed registers in `DeserializeRegister` retain exact v0–v3 rejection
  semantics and MUST NOT silently fall back to the default expression.
- Any `DeserializeRegister` default expression that is shadowed during
  substitution is still included in the structural `VerifyStark` preflight scan
  (Section 3.1) so availability and stale-node policies cannot be bypassed by
  shadowed defaults.

## 2. Canonical Statement & Chunked Proof Transport

### 2.1 Canonical Statement (`ErgoStatementV1`)

Before invoking any profile runtime, the host constructs the exact canonical
`ErgoStatementV1` byte sequence:

```text
ErgoStatementV1 =
    ASCII("Ergo.VerifyStark.Statement")  // 26 bytes
 || u8(0x01)                             //  1 byte  (statement version)
 || chainDomainId                        // 32 bytes (height-1 genesis Header.id)
 || profileId                            // 32 bytes (selected profile digest)
 || programId                            // 32 bytes (guest program digest)
 || BLAKE2b-256(SELF.propositionBytes)   // 32 bytes (executing contract digest)
 || u32le(applicationPayload.length)     //  4 bytes
 || applicationPayload                   //  N bytes (0 <= N <= maxApplicationPayloadBytes)
```

- Fixed prefix length: **159 bytes** (`26 + 1 + 32 + 32 + 32 + 32 + 4`).
- `chainDomainId` is the 32-byte height-1 genesis block `Header.id` (e.g.,
  mainnet vs testnet domain separation).
- Each profile specifies how its guest commits to `ErgoStatementV1` (typically
  `BLAKE2b-256(ErgoStatementV1)` in the profile's canonical public outputs).

### 2.2 Canonical Proof Chunking (`proofChunks`)

Because ErgoScript `Coll[Byte]` values and context-extension entries are subject
to per-value size ceilings (`MaxByteArraySize = 65,535` bytes), proofs are
passed as `Coll[Coll[Byte]]` with a unique canonical partition.

Each active profile defines an admissible proof byte range
`[minProofBytes, maxProofBytes]` (`1 <= minProofBytes <= maxProofBytes`):

- Fixed-seal profiles set `minProofBytes == maxProofBytes`.
- Bounded Merkle-multiproof profiles (such as STIR or WHIR) set
  `minProofBytes < maxProofBytes` to allow exact compressed proof lengths up to
  the profile's worst-case byte ceiling.

Given `proofChunks = [c_0, ..., c_{k-1}]`, the partition is valid if and only
if ALL of the following hold:

1. `k >= 1`;
2. for every non-final chunk `0 <= i < k - 1`, `c_i.length == 65,535`;
3. for the final chunk `c_{k-1}`, `1 <= c_{k-1}.length <= 65,535`;
4. `totalBytes = sum(c_i.length)` satisfies `minProofBytes <= totalBytes <= maxProofBytes`.

Every admissible proof byte string therefore has exactly one valid chunking. Any
non-canonical partition (empty collection, zero-length chunk, non-maximal
non-final chunk, or total length outside `[minProofBytes, maxProofBytes]`)
returns `false` after precharge without invoking the verifier runtime.

## 3. Whole-Input Preflight, Evaluation & Costing Order

### 3.1 Structural Preflight Scan (`preflightFullReduction`)

For ErgoTree v4+, after single-pass `DeserializeContext`/`DeserializeRegister`
substitution completes, the interpreter performs an iterative left-to-right DFS
structural scan across all serializer-owned `Value` children of the substituted
proposition and any shadowed `DeserializeRegister` defaults (including dead
branches and lambda bodies), without evaluating user expressions.

Each structural `VerifyStark` occurrence has its `profileId` child classified
statically:

- `StaticStarkProfileId(bytes)`: `ByteArrayConstant` or `ConstantPlaceholder`
  resolving to an exact 32-byte constant;
- `MalformedStarkProfileId`: constant or placeholder that does not resolve to
  32 bytes;
- `DynamicStarkProfileId`: any non-constant expression.

### 3.2 Capability & Future-Generation Policy (`evaluateStarkPolicy`)

The host supplies a `StarkVerificationCapability` (`Unavailable` or an immutable
transition `Snapshot`) carrying:

- `chainDomainId` (32 bytes);
- `starkGeneration` (monotone integer `G >= 1`, Section 4);
- `maxSupportedStarkGeneration` (`Gmax >= 1`, highest generation compiled into
  the node binary);
- `transitionId` (32-byte on-chain transition commitment);
- `validationPurpose`: `HistoricalBlockValidation`, `AdmissionValidation`,
  `CandidateConstruction`, or `ProverReduction`;
- `dispatchJit` (`> 0`) and sorted `ProfileEntry` list (`Active` or `Quarantined`).

Before any user expression or `dispatchJit` executes:

1. **Zero structural occurrences**: ordinary v4 scripts without `VerifyStark`
   proceed identically regardless of `Unavailable` or `Snapshot`.
2. **At least one occurrence + `Unavailable`**: MUST throw
   `OpcodeUnavailableException(0xB9)`.
3. **At least one occurrence + future generation (`G > Gmax`)**:
   - Under `HistoricalBlockValidation`: if EVERY structural occurrence has a
     `StaticStarkProfileId` explicitly present (`Active` or `Quarantined`) in
     the binary's last known snapshot `Tmax`, evaluation proceeds normally under
     `Tmax`; otherwise the whole input soft-fork-accepts (`TrueProp` at
     `preflightBlockCost`) before any user logic executes.
   - Under `AdmissionValidation`, `CandidateConstruction`, or
     `ProverReduction`: MUST fail closed with
     `StarkUnsupportedFutureGenerationException(G, Gmax)`. Stale nodes never
     relay, mine, or sign transactions under an unknown STARK generation.
4. **Supported generation (`G <= Gmax`)**: normal evaluation proceeds.

### 3.3 Runtime Evaluation & Phased Precharge Order

When a `VerifyStark` node executes under an active `Snapshot`, steps MUST run
in this exact order:

1. Evaluate `profileId` ONLY (heavy children `proofChunks`, `applicationPayload`,
   and `programId` MUST NOT be evaluated yet).
2. Charge `dispatchJit` unconditionally.
3. If `profileId.length != 32`, return `false`.
4. Binary-search `profileId` (unsigned lexicographic order) in the snapshot:
   - **Absent**: return `false`.
   - **Quarantined**: throw `StarkProfileQuarantinedException(profileIdHex)`.
     Quarantine MUST throw (fail closed) and MUST NEVER return `false`, so
     `!verifyStark(...)` cannot turn a quarantined profile into `true`.
   - **Active**: proceed to step 5.
5. Charge `active.fixedJit` unconditionally BEFORE evaluating any remaining
   child or allocating proof buffers.
6. Evaluate `programId`; if `programId.length != 32`, return `false`.
7. Evaluate `applicationPayload`; if
   `applicationPayload.length > active.maxApplicationPayloadBytes`, return
   `false`.
8. Evaluate `proofChunks` and validate canonical chunking against
   `[minProofBytes, maxProofBytes]` (Section 2.2); if invalid, return `false`.
9. Construct canonical `ErgoStatementV1` with
   `contractId = BLAKE2b-256(SELF.propositionBytes)`.
10. Invoke `active.runtime.verify(statement, programId, chunkArrays)` and return
    its deterministic `Boolean` result.

Any internal verifier exception other than `CostLimitException` MUST fail closed
(never silently return `true`).

## 4. Network Lifecycle Decoupled from `BlockVersion`

Ergo's ErgoTree header carries a 3-bit version field (values `0..7`), tied to
`BlockVersion`. Using `BlockVersion` for STARK profile additions, repricing, or
emergency quarantine would exhaust Ergo's protocol version space and bind
emergency quarantine to a full multi-month block-version soft-fork cycle.

EIP-0045 therefore decouples STARK profile lifecycle from `BlockVersion`:

1. **Opcode activation (one-time soft-fork)**: ErgoTree v4 (`BlockVersion`
   activation + rule `1002` adding `0xB9`) activates the `0xB9` opcode shell
   once.
2. **Profile lifecycle (`starkGeneration` + `transitionId`)**: Subsequent
   profile additions, nondecreasing `dispatchJit`/`fixedJit` repricing, and
   emergency profile quarantine advance a dedicated monotone on-chain parameter
   `starkGeneration` paired with an on-chain 32-byte `transitionId` digest
   committing to the exact canonical transition snapshot (`chainDomainId`,
   `starkGeneration`, `dispatchJit`, and sorted `(profileId, state, fixedJit)`
   entries).
3. **Transition invariants**:
   - Compiled profiles are immutable: a `profileId` never changes verifier code
     or acceptance semantics.
   - Repricing is nondecreasing across generations so historical blocks remain
     cost-valid under older snapshots.
   - Quarantine is monotonic and fail-closed: once a `profileId` is
     `Quarantined`, it stays `Quarantined` in all subsequent generations; a
     patched verifier MUST be introduced under a brand-new `profileId`.
4. **Open Ergo Core governance items** (to be finalized with Ergo core
   maintainers during node integration PR):

| Governance Item | Proposed Default | Maintainer Decision Needed |
|---|---|---|
| ErgoTree v4 + `0xB9` activation | Standard soft-fork (90% voting, rule `1002`) | Confirm activation coupling with next scheduled soft-fork |
| `starkGeneration` & `transitionId` storage | Dedicated on-chain `Parameters` / header extension entry | Assign exact Ergo parameter ID(s) and update validation rule |
| Emergency quarantine voting threshold / window | Shorter emergency epoch window than standard soft-fork | Confirm whether quarantine uses a faster miner-voting parameter update |
| Standalone transaction size policy | **300 KiB** (or 256 KiB floor) | Confirm 256 KiB vs 300 KiB relay ceiling (Section 9) |

## 5. Contract Author Safety

Contracts calling `verifyStark` MUST observe the following safety rules:

1. **Pin `(profileId, programId)` pairs**: `programId` is only meaningful within
   a specific `profileId`. Always compare or hardcode BOTH 32-byte identifiers.
2. **Provide a recovery / escape path gated by lazy `if` BEFORE `verifyStark`**:
   Because an active profile may be quarantined if a soundness bug is
   discovered, contracts locking user funds SHOULD gate a height-timelocked
   recovery or governance fallback with a lazy `if` expression so `verifyStark`
   is never evaluated along the recovery branch:
   ```scala
   if (HEIGHT > recoveryHeight) {
     ownerPk
   } else {
     sigmaProp(verifyStark(chunks, payload, programId, profileId))
   }
   ```
   **Warning**: `SigmaProp || SigmaProp` (`SigmaOr`) evaluates ALL branches
   eagerly without short-circuiting. Writing `ownerPk || sigmaProp(verifyStark(...))`
   will still evaluate `verifyStark` and fail with
   `StarkProfileQuarantinedException` if `profileId` is quarantined. Only lazy
   `if` (or pure `Boolean || Boolean` via `BinOr` where both operands are
   `Boolean`) prevents evaluating `verifyStark` on the recovery path.
3. **Never rely on `!verifyStark(...)`**: Quarantine throws
   `StarkProfileQuarantinedException` rather than returning `false`, and
   future-generation stale-node fallback skips user logic altogether. Never gate
   a challenge or fallback branch on negated `verifyStark`.
4. **Bind transaction effects inside `applicationPayload`**: `ErgoStatementV1`
   automatically binds `chainDomainId`, `profileId`, `programId`, and
   `BLAKE2b-256(SELF.propositionBytes)`. It does NOT automatically bind
   `SELF.id`, `INPUTS`, `OUTPUTS`, registers, or nullifiers. Contracts MUST
   serialize every security-critical box/output/nullifier commitment into
   `applicationPayload` (or hash them into a 32-byte commitment passed as
   `applicationPayload`).
5. **Compile explicitly for ErgoTree v4**: `SigmaTyper` rejects `verifyStark`
   under ErgoTree v0–v3.

# Part II — Verifier Profile Admission (Mainnet Gate)

No concrete verifier profile is activated by Part I alone. Every candidate
profile (starting with Profile v1) MUST be proposed in a dedicated, immutable
profile specification and pass ALL of the following gates before activation.

## 6. Cryptographic & Soundness Requirements

1. **Minimum provable soundness**: At least **128-bit provable classical
   soundness** verified using an exact pinned commit of
   [`ethereum/soundcalc`](https://github.com/ethereum/soundcalc) under a
   published proximity-gap regime (Unique Decoding Regime or Johnson Bound
   Regime).
   - Conjectured up-to-capacity bounds (e.g., toy-model estimates relying on
     conjectures disproved by Crites & Stewart, ePrint 2025/2046, and Krachun,
     Kazanin & Haböck, ePrint 2026/782) are **NOT admissible**.
   - The field extension size MUST exceed $2^{128}$ (e.g., Goldilocks³ at
     $\approx 2^{192}$ or KoalaBear⁵ at $\approx 2^{155}$; BabyBear⁴ at
     $\approx 2^{123.6}$ is mathematically disqualified).
2. **Whole-architecture coverage**: The 128-bit bound and security argument
   MUST cover **every** reachable circuit in the profile's recursion/compression
   pipeline (leaf, aggregation/join, and final compression stages), not solely
   the outermost layer.
3. **Hash conservatism**: Profiles using a standard symmetric hash (such as
   BLAKE3) for outermost Merkle authentication and Fiat-Shamir transcripts are
   preferred over profiles relying solely on newer algebraic hashes (such as
   Poseidon2) at the L1 consensus boundary.
4. **Post-quantum posture**: A ≥128-bit classically sound hash-based STARK
   provides ≥64-bit Grover quantum soundness for the proof system itself, while
   overall transaction security remains governed by Ergo's existing L1
   signature and Blake2b-256 primitives. This EIP makes no end-to-end
   post-quantum claim.
5. **Independent cryptographic audit & permissive license**: The upstream proof
   system and verifier specification MUST be under an OSI-approved permissive
   license (MIT, Apache-2.0, or CC0) compatible with `sigmastate-interpreter`,
   and the frozen release MUST have an independent public security audit.

## 7. Verifier Implementation & Deterministic Costing

1. **Pure-JVM implementation (Java 8 compatible)**: The reference verifier in
   `sigmastate-interpreter` MUST be pure Scala/JVM compatible with Ergo's CI
   target (`adopt@1.8`) with zero JNI, native libraries, floating-point math, or
   non-deterministic iteration order.
2. **Canonical proof format & strict bounds**: Every field element, public
   output, tag, and byte length MUST be canonically validated with strict EOF
   before/during verification; general-purpose compression codecs (such as
   `zstd` or `bincode`) MUST NOT enter consensus verification.
3. **Content-addressed `profileId`**: Each profile fixes a canonical manifest
   (specifying upstream release pin, verifier constants/VKs, proof byte bounds
   `[minProofBytes, maxProofBytes]`, `maxApplicationPayloadBytes`, and statement
   binding) whose `BLAKE2b-256` digest defines its immutable `profileId`.
4. **Worst-case JVM metering (`dispatchJit`, `fixedJit`)**: `fixedJit` MUST be
   calibrated from worst-case JVM verification benchmarks (`maxProofBytes`,
   maximum recursion/multiproof work) against Ergo's per-block cost budget so
   block validation latency remains bounded even under adversarial transactions.

## 8. Conformance & Node Readiness

Before a profile transition is proposed for activation:

1. **Differential Rust / JVM conformance suite**: Reproducible positive proofs
   generated by the pinned upstream prover covering every admitted terminal
   path, plus targeted negative mutations covering every structural boundary
   (wrong `chainDomainId`, `profileId`, `programId`, `contractId`, payload bit
   flip, non-canonical chunking, non-canonical field elements, truncated/padded
   bytes, invalid Merkle/folding/PoW checks), all verified to agree between the
   upstream Rust verifier and the JVM verifier.
2. **Independent code & consensus review**: Independent review of the JVM
   verifier port, cost calibration, and transition snapshot.
3. **Node integration & testnet soak**: Mempool admission rate-limiting for
   unpaid STARK verification attempts, block/candidate/reorg integration tests,
   and testnet verification of realistic transactions.

## 9. Transaction Size Policy (256 KiB vs 300 KiB)

Ergo's current node transaction-size policy rejects standalone transactions
carrying modern 128-bit STARK proofs (~200–292 KiB). Raising the node policy
ceiling is required for single-transaction settlement:

- **256 KiB (262,144 B)** accommodates compact STIR profiles such as ZisK
  `Final_Compressed` (240 KiB expected / 247 KiB worst-case) with ~9–16 KiB
  headroom for transaction inputs, outputs, and signatures.
- **300 KiB (307,200 B)** aligns with the Ethereum Foundation's Milestone M3
  (December 2026) 128-bit zkEVM proof ceiling (`≤ 300 KiB`) and accommodates
  all major 128-bit STIR and WHIR candidates (ZisK ≤ 247 KiB, Pico `compress`
  292 KiB, Venus ≤ 274 KiB) with comfortable transaction overhead.

A **300 KiB** standalone transaction policy (paired with bounded per-block and
mempool admission controls) is RECOMMENDED; final ceiling selection is left to
Ergo core maintainers during node integration.
